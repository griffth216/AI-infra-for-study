## 1. 问题动机（3 min）—— GEMM 已逼近极限，非 GEMM 是最后的主战场

**要讲什么：**

- GEMM 优化已逼近硬件天花板：NVIDIA cuBLAS/CUTLASS 经过十余年迭代，FP8 Tensor Core 利用率已达 80-90%，留给手工优化的空间极小
- 图 1：BF16 vs FP8 训练 LLaMA-3 1B 的 GPU 时间占比
  - GEMM：47% → 33%（被 FP8 加速，优化空间压缩）
  - Others：17% → 28%（暴涨，成为新的最大瓶颈）
  - Attention + Optimizer 占比基本不变
- 阿姆达尔定律的审判：GEMM 被 FP8 加速两倍后，非 GEMM 操作占比从 53% → 67%
- 本质矛盾：Tensor Core 算力翻倍增长（H100 FP8 = 3958 TFLOPS），但 HBM3 带宽仅 3.35 TB/s → Memory Wall
- "未来升级 FP4，非 GEMM 占比只会更高——GEMM 已经不是瓶颈了，Memory 才是"

**强调什么：**
- **一句话点题**："GPU 绝大部分时间没在做矩阵乘法，而是在等显存搬运数据"
- 具现化（Materializing）中间张量的代价——这是贯穿全文的"反派"
- GEMM 优化已是红海，非 GEMM 融合才是蓝海——这是 CODA 存在的理由

## 2. CODA 的核心思路（3 min）—— 不动 GEMM，只动尾部

**要讲什么：**

- **核心洞察**：许多在框架层表现为独立算子的非 GEMM 操作，可以通过代数重构变成"矩阵乘法算完后顺手做的小计算"
- **一张图讲清楚**（图 2）：顶行传统做法（粉白相间，每个白块 = 一次 HBM 往返）→ 底行 CODA 做法（白块被"吞噬"进粉色 GEMM 块的尾部）
- 图 3：Main Loop（固定不动，专家的领地）→ Epilogue（可编程，CODA 的战场）→ 写回 HBM
- 核心公式：GEMM: $h = xW$，Epilogue: $y[i,j] = f[i,j](h[i,j])$
- **唯一硬约束**：tile-locality —— Epilogue 只能看到当前分块的数据，不能跨块通信

**强调什么：**
- CODA **不碰** GEMM 主循环——那是 CUTLASS 专家用十年磨出来的，改了反而可能变慢
- CODA 的策略是"寄生"：在 GEMM 算完、数据还在寄存器里热乎着的时候，顺手把非 GEMM 操作干掉
- 这是"借鸡生蛋"——GEMM 反正要把数据从寄存器搬到 HBM，搬之前多做一步几乎零成本

## 3. 传统方法的困境（2 min）—— 为什么手写融合走不远

**要讲什么：**

### 3.1 前向融合 ≠ 反向能用（1 min）

- **数学公式变了**：前向 SwiGLU $f(x) = \text{silu}(x_g) \odot x_u$，反向求导公式包含 sigmoid 导数、指数、乘法链路——完全不同
- **前向省掉的中间结果，反向又要回来**：反向求导需要前向的 $x$，但前向为了省带宽没写回——要么妥协写回（打破融合初衷），要么重计算（增加逻辑复杂度）
- **数据流方向反了，内存对齐全乱了**：前向按行读取（Row-major），反向矩阵转置后变成按列读取（Column-major），合并访存被破坏

### 3.2 手写融合的工程代价（1 min）

- 前向手工写一套 CUDA/Triton kernel，反向**必须原封不动再受一遍苦**——手写对应的反向融合 kernel
- FlashAttention 前向出来后，反向等了好几个月才出来——同一个团队、同一个算子，只是方向反了
- **结论**："前向 GEMM + Epilogue"如果不能让反向自动继承，就没有从根本上解决问题

**强调什么：**
- 这是 CODA 论文 2.1 节的核心论点，也是 CODA 要解决的根本问题——不是"做一次融合"，而是"做一套框架让前后向都能自动融合"
- 为后面的 Theorem 1 做铺垫：CODA 的数学贡献就是证明了"只要前向是 tile-local，反向自动 tile-local"

## 4. 五大原语：CODA 的工具箱（2 min）

**要讲什么：**

在讲具体的代数重构之前，先挂出 CODA 提供的五类原语。这里只讲"每类能干什么"，不讲实现细节，后面每个模式会引用。

| 原语 | 做什么 | 硬件位置 | Transformer 对应 |
|------|--------|---------|-----------------|
| Elementwise/Pairwise Map | 逐元素/成对变换 | 寄存器内 | SwiGLU, RoPE, 残差加法 |
| Vector Load/Store | 广播一维向量到 tile | Shared Memory | RMSNorm 的 γ 权重 |
| Tile Load/Store | TMA 异步搬运二维块 | HBM ↔ Shared Memory | 残差流、保存激活值 |
| Tile Reduction | 分块内局部规约 | Warp Shuffle | RMS 平方和、Cross Entropy LSE |
| Stateful Transform | 寄存器内状态机 | 寄存器 + 状态变量 | Online Softmax 的 m, l 统计量 |

**强调什么：**
- 五类原语非常精简——这不是设计上的巧合，而是刻意为之：只暴露"能高效映射到 GPU 硬件"的操作，不给任何可能破坏性能的灵活性
- 你的 Week 1 学过的 Online Softmax 的 running max/sum 就是 Stateful Transform——**这个思想你早就见过了**

### 5.1 GEMM-Residual-RMSNorm-GEMM（3 min）

**公式：**

$$y = \text{RMSNorm}(xW_0 + z, \gamma)W_1 = (r(xW_0 + z) \odot \gamma)W_1$$

其中 $z$ 是残差流，$r = 1 / \text{rms}(xW_0 + z)$ 是行向均方根倒数因子。

这个模式横跨 Attention 输出投影 → 残差 → RMSNorm → MLP 门控投影（以及 MLP 降级投影 → 残差 → RMSNorm → QKV 投影等共 3 处）。

**传统做法：**
1. `GEMM1`：算 $h_0 = xW_0$，写回 HBM
2. 从 HBM 读回 $h_0$，算 $h_0 + z$，再算 RMSNorm
3. RMSNorm 需要在隐藏维度（d=4096~8192）上做全局平方和 → 所有线程阻塞等待标量 $r$ 算完
4. 用 $r$ 缩放后写回 HBM，再读回做 `GEMM2`
- **致命缺陷**：两个 GEMM 之间被 RMSNorm 的全局同步硬生生阻断，GPU 大量时间在等

**CODA 优化后的计算流水线：**

1. **GEMM1**：$h_0 = xW_0$
2. **Epilogue1**（GEMM1 的尾部，寄存器内完成）：
   - $h_1[i,j] = h_0[i,j] + z[i,j]$（残差加，Elementwise Map）
   - $h_2[i,j] = h_1[i,j] \odot \gamma[j]$（RMSNorm 权重缩放，Vector Load 广播 γ）
   - $\hat{r}[i,j] = \text{partialRMS}(h_1[i,j])$（局部平方和，Tile Reduction）
3. **微型辅助 kernel**：合并所有 tile 的 $\hat{r}$（~32 个标量）→ 得到全局 $r$
4. **GEMM2**：$h_3 = h_2 W_1$（**此时不需要 $r$，直接开始算！**）
5. **Epilogue2**（GEMM2 的尾部）：$y[i,j] = r[i] \cdot h_3[i,j]$（最后才乘 $r$）

**代数证明（核心 trick —— 数乘结合律）：**

$$y = (r(xW_0 + z) \odot \gamma)W_1 = r((xW_0 + z) \odot \gamma)W_1$$

因为 $r$ 是一个标量（整行共享同一个值），矩阵乘法对标量乘法满足结合律。因此 $r$ 可以从 $W_1$ 的左侧"提取"到最外层，延迟到 GEMM2 结束后才应用。

$r$ 的两级规约之所以可行，是因为：
$$\sum_{i=1}^{D} u_i^2 = \sum_{\text{tiles}} \sum_{i \in \text{tile}} u_i^2$$

每个 tile 只产出 1 个标量，辅助 kernel 的输入量从 $O(D)$ 降为 $O(\text{num\_tiles})$。

**用的原语：** Elementwise Map、Vector Load、Tile Reduction

**代码展示 —— 完整的三步编排（对应论文 3.2.1 的流水线）：**

```python
# coda/models/ops.py — 将代数重构翻译为三个硬件步骤
def gemm_residual_rmsnorm_gemm_fwd(x, y, w_a, w_b, w_n, ...):
    # Step 1: GEMM1 + Residual + ×γ + 局部平方和 → 一个融合 kernel
    #   对应论文: h₀ = xW₀, Epilogue1: +z, ×γ, partialRMS
    x_out, s, h = gemm_residual_partial_rmsnorm(
        A=y, B=w_a, C=x, W=w_n, block_size=block_size_norm)

    # Step 2: 微型辅助规约 → 合并局部统计量得到全局 r
    #   对应论文: r = 1/sqrt(reduce(partialRMS) + ε)
    rstd_out = compute_rstd(s=s, eps=eps)

    # Step 3: GEMM2 + 延迟缩放 → r 在 Epilogue 中应用
    #   对应论文: h₃ = h₂W₁, Epilogue2: y = r · h₃
    z_out = gemm_rmsnorm(A=h, B=w_b, R=rstd_out)

    return x_out, y_out, z_out, rstd_out
```

### 5.2 Pairwise Activations：SwiGLU / RoPE（3 min）

**公式：**

$$h = xW, \quad h_a[i,j], h_b[i,j] = \text{split}(h[i,j]), \quad y[i,j] = f[i,j](h_a[i,j], h_b[i,j])$$

- SwiGLU：$f(g, u) = \text{silu}(g) \odot u$（两输入 → 一输出，降维）
- RoPE：$f(x_{2k}, x_{2k+1}) = (x_{2k}\cos\theta - x_{2k+1}\sin\theta,\; x_{2k}\sin\theta + x_{2k+1}\cos\theta)$（两输入 → 两输出，保维）

**传统做法：**
1. GEMM 算出膨胀的中间矩阵 $H$（SwiGLU 需要 gate+up 两倍宽度，$D \to 2D$）
2. 将膨胀矩阵 $H$ 完整写回 HBM（FP16 下可达数百 MB）
3. 启动独立激活 kernel，从 HBM 读取 $H$，跨半个矩阵去拉取 $h_a[j]$ 和 $h_b[j]$（它们分别位于 $H$ 的前半和后半，物理距离 = D 个元素）
4. 算完再写回
- **致命缺陷**：中间膨胀矩阵产生了两次完整 HBM 往返，且配对元素物理距离远导致 cache miss

**CODA 优化的计算流水线：**

核心思路分为**算法层**和**硬件层**两步，缺一不可：

**第一步（算法层）—— 权重列交错重排**（离线，加载时一次性完成）：
- 传统 $W = [W_{a,0},...,W_{a,D-1}, W_{b,0},...,W_{b,D-1}]$
- CODA $W_{\text{interleaved}} = [W_{a,0}, W_{b,0}, W_{a,1}, W_{b,1}, ..., W_{a,D-1}, W_{b,D-1}]$
- 效果：原本相隔 $D$ 列的 $h_a[j]$ 和 $h_b[j]$，在输出向量中变为物理相邻（位置 $2j$ 和 $2j+1$）

**第二步（硬件层）—— Hopper 累加器布局暴露**（这是全文最关键的一条硬件依赖）：
- NVIDIA Hopper 架构（H100/H200）在 Epilogue 阶段向程序员**暴露了 Tensor Core 累加器的物理分布规律**：
  > "输出向量中物理相邻的元素（如第 $2j$ 和 $2j+1$ 个元素），在 GEMM 计算结束时，天然且必然同时躺在同一个 Warp 内同一个线程（Thread）的寄存器里。"
- 这不是所有 GPU 都有的特性——消费级显卡（如 RTX 4060 Ada Lovelace）或不开放累加器布局的架构上，相邻元素可能分布在不同线程中，此时做配对就需要跨线程 shuffle 或 shared memory 交换，CODA 的零开销优势会被直接击穿

**第三步 —— 黄金闭环**：
1. 算法重排使得：需要配对的特征，排在输出维度的**相邻位置**（$2j$ 和 $2j+1$）
2. Hopper 累加器布局保证：相邻位置的输出值，恰好被分配在**同一个线程的寄存器**中
3. **闭环**：线程一低头，发现自己寄存器里的两个数恰好是需要配对的两个 → 直接应用 $f$，零显存交通流，零跨线程通信

**CODA 优化后的优势：**

| 维度 | 传统做法 | CODA |
|------|---------|------|
| HBM 写回次数 | 2-3 次（GEMM 输出 + 激活结果） | 1 次（仅最终结果） |
| 中间膨胀矩阵 | 完整写回 HBM（SwiGLU 需要 2× 宽度） | 从未离开寄存器 |
| 配对数据获取 | 跨半个矩阵读取（cache miss 严重） | 同寄存器内相邻，零延迟 |
| Kernel launch 数 | 2（GEMM + 独立激活 kernel） | 1（融合） |

**代数证明（为什么权重交错重排是合法的）：**

矩阵乘法 $h = xW$ 中，输出列 $j$ = $\sum_k x_k \cdot W_{k,j}$。将 $W$ 的列重排等价于将 $h$ 的列按相同规则重排——因为矩阵乘法的每列是独立计算的，列的顺序不影响计算结果，只影响输出布局。将 $W_a$ 和 $W_b$ 的列交错插入后，输出向量中原本相隔 $D$ 的 $h_a[j]$ 和 $h_b[j]$ 变为物理相邻（位置 $2j$ 和 $2j+1$）。

Pairwise Map 的降维（SwiGLU）和保维（RoPE）都是合法的，因为每个 $(2j, 2j+1)$ 对的计算不依赖其他对。降维时 Epilogue 自动压缩输出布局（$N \to N/2$），保维时维持布局不变。

**用的原语：** Pairwise Map

### 5.3 Cross-Entropy Loss（2 min）

**公式：**

$$h_i = x_i W_{lm}, \quad \ell_i = -h_{i, y_i} + \log\sum_{k=1}^{V}\exp(h_{i,k})$$

其中 $V$ 为词表大小（LLaMA-3 为 128K，典型场景 ≥ 32K）。

**传统做法：**
1. GEMM 算出 $B \times L \times V$ 的 Logits 矩阵（batch=2, seq=4096, V=32000 → FP16 下约 500MB）
2. 完整写回 HBM
3. 启动 Softmax kernel，从 HBM 重新读出完整 Logits → 算 LSE → 算 loss
- **致命缺陷**：Logits 矩阵是训练中最大的单次 HBM 写入之一，纯粹的访存瓶颈

**CODA 优化的计算流水线：**

1. **GEMM**：分块（每次产出 256 个 logits，仍驻留在寄存器）
2. **Epilogue1**（寄存器内，不写回 Logits）：
   - 检查 target label $y_i$ 是否在本块 → 如果是，寄存 $h_{i,y_i}$
   - 算本地 max + sum-exp（Stateful Transform 维护 running m, l）
   - 只把分块统计量（几个标量）写回 HBM
3. **微型辅助 kernel**：合并所有 tile 的 local max/sum-exp → 得到全局 LSE → 代入公式算出 $\ell_i$

**CODA 优化后的优势：**

| 维度 | 传统做法 | CODA |
|------|---------|------|
| HBM 写入量 | 完整 Logits 矩阵（$B \times L \times V$，FP16 下可达 500MB-1GB） | 仅分块统计量（每个 tile 几个标量，总计几 KB） |
| 显存占用 | 极高，随词表增长极易 OOM | 近乎为零（不保存完整 Logits 中间矩阵） |
| HBM 读取次数 | Softmax kernel 重新从 HBM 完整读取 Logits | 不需要重新读取（辅助 kernel 只读几 KB 统计量） |
| Kernel launch 数 | 2（GEMM + Softmax/Loss） | 2（融合 GEMM + 微型辅助 kernel） |

> 虽然 kernel launch 数没减少，但第二个 kernel 的输入从 500MB 的 Logits 矩阵变成了几 KB 的分块统计量——**同样的 launch 次数，I/O 量差了 5 个数量级。**

**代数证明（两级 LSE 合并的合法性）：**

这是 Online Softmax 的经典公式。设分块 $t$ 的局部最大值为 $m_t$，局部指数和为 $s_t = \sum_{k \in t} \exp(h_k - m_t)$：

$$m_{\text{global}} = \max_t m_t, \quad s_{\text{global}} = \sum_t s_t \cdot \exp(m_t - m_{\text{global}})$$

然后 $\log\sum\exp(h) = m_{\text{global}} + \log(s_{\text{global}})$。这个递推公式是精确的，没有近似。

**用的原语：** Stateful Transform、Tile Reduction

## 6. 反向传播：Theorem 1 与 RMSNorm 特例（7 min）

### 6.1 Theorem 1 —— 前向 tile-local → 反向自动 tile-local（4 min）

#### 从最简单的模型推导（搭建理解阶梯）

考虑由 element-wise 激活函数 $f$ 隔开的两个 GEMM：

**前向传播：**
$$h = xW_0, \quad h' = f(h), \quad y = h' W_1$$

其中 $f$ 是逐元素激活（如 ReLU、GeLU、SiLU），每个位置的输出只依赖同位置的输入。

**反向传播（链式法则逐步推导）：**

已知上游回传的损失梯度 $\nabla_y \mathcal{L} \in \mathbb{R}^{1 \times M}$，我们需要求三层梯度：

**Step 1：求 $\nabla_{h'}\mathcal{L}$——这是上一个 GEMM 的贡献**
$$\nabla_{h'}\mathcal{L} = \nabla_y \mathcal{L} \cdot W_1^{\top}$$
- 数学实体：$(1 \times M) \times (M \times D) \to (1 \times D)$
- **计算类型：标准 GEMM**（矩阵乘法）

**Step 2：求 $\nabla_h \mathcal{L}$——穿过激活函数的导数**
$$\nabla_h \mathcal{L} = \nabla_{h'}\mathcal{L} \odot f'(h)$$
- 数学实体：$(1 \times D) \odot (1 \times D) \to (1 \times D)$
- **计算类型：逐元素 Hadamard 积**（Element-wise，tile-local）

**Step 3：求 $\nabla_x \mathcal{L}$——再穿过一个 GEMM**
$$\nabla_x \mathcal{L} = \nabla_h \mathcal{L} \cdot W_0^{\top}$$
- 数学实体：$(1 \times D) \times (D \times K) \to (1 \times K)$
- **计算类型：标准 GEMM**（矩阵乘法）

#### 关键观察：结构完全对称

把前向和反向的计算链并排对比：

| | Step 1 | Step 2 | Step 3 |
|------|--------|--------|--------|
| **前向** | GEMM ($W_0$) | 本地变换 $f(h)$ | GEMM ($W_1$) |
| **反向** | GEMM ($W_1^{\top}$) | 本地变换 $\odot f'(h)$ | GEMM ($W_0^{\top}$) |

**它们拥有完全一模一样的拓扑结构：GEMM → tile-local 变换 → GEMM。**

唯一的区别是**融合方向**（图 9）：
- 前向：$f$ 融合在**产生** $h$ 的 GEMM（$W_0$）的 Epilogue → **前融**
- 反向：$\odot f'(h)$ 融合在**产生** $\nabla_{h}\mathcal{L}$ 的 GEMM（$W_0^{\top}$）的 Epilogue → **后融**

#### Theorem 1 的推广：从单层到 L 层

前向（含 $L-1$ 个 GEMM-Epilogue 块 + 最终 GEMM）：
$$h_\ell = x_{\ell-1}W_\ell, \quad x_\ell[i,j] = f_\ell[i,j](h_\ell[i,j]), \quad \ell=1,...,L-1$$
$$h_L = x_{L-1}W_L$$

Theorem 1 结论（反向保持完全相同的结构）：
$$\nabla_{x_{\ell-1}}\mathcal{L} = \nabla_{h_\ell}\mathcal{L} W_\ell^{\top} \quad\text{(GEMM)},\qquad \nabla_{h_{\ell-1}}\mathcal{L}[i,j] = g_{\ell-1}[i,j](\nabla_{x_{\ell-1}}\mathcal{L}[i,j], h_{\ell-1}[i,j]) \quad\text{(tile-local Epilogue)}$$
$$\nabla_{W_\ell}\mathcal{L} = x_{\ell-1}^{\top}\nabla_{h_\ell}\mathcal{L} \quad\text{(标准 GEMM，权重梯度独立计算)}$$

#### 为什么成立？—— 雅可比矩阵的分块对角性（证明直觉）

对于 Epilogue $x_\ell[i,j] = f_\ell[i,j](h_\ell[i,j])$，由于 $f_\ell[i,j]$ **仅依赖当前分块 $[i,j]$**（tile-locality 约束）：

- 全矩阵的雅可比 $\frac{\partial x_\ell}{\partial h_\ell}$ 是一个**分块对角矩阵**——每个分块 $[i,j]$ 的导数只和自己在同一个分块上
- 反向传播的链式法则：$\nabla_{h_\ell}\mathcal{L} = (\frac{\partial x_\ell}{\partial h_\ell})^{\top} \cdot \nabla_{x_\ell}\mathcal{L}$
- 因为雅可比是分块对角的，其转置也是分块对角的 → $\nabla_{h_\ell}\mathcal{L}[i,j]$ **只依赖** $\nabla_{x_\ell}\mathcal{L}[i,j]$（同一个分块）
- 定义 $g_\ell[i,j]$ 为 $f_\ell[i,j]$ 的 VJP → $g_\ell$ **也天然是 tile-local 的**

**关键结论：反向传播没有引入任何新的跨分块通信。** 计算 $\nabla_{h_{\ell-1}}\mathcal{L}[i,j]$ 所需的所有材料，天然就在当前 GEMM 的寄存器里。

#### Theorem 1 的两个落地价值

**价值一：理论的普适性（Generality）——统一的融合判定准则**

在这之前，SwiGLU（降维）、RoPE（保维）、各种激活函数反向梯度（升维）——每种操作的融合都必须单独论证可行性。Theorem 1 用雅可比矩阵的物理性质一言蔽之：**只要前向尾部处理具备 tile-locality，其反向求导规则在数学上就必然也具备 tile-locality。** 不再有特例。

**价值二：工程的自动化（Automaticity）——从"手写独立 kernel"到"复用同一套 Epilogue 模板"**

Theorem 1 的工程价值需要精确表述——它不意味着编译器能自动求导：

- **T1 不能做什么**：编译器不会自动推导 $\text{silu}'(x)$ 的数学公式。每个激活函数的反向规则（VJP）仍然需要由人（或 LLM）来写——`_dswiglu_op` 里的 `dswiglu(x=g, y=u, dout=dout)` 就是单独实现的。
- **T1 能做什么**：它保证了反向计算**一定可以**写成 GEMM + tile-local Epilogue 的形式。这意味着：
  - 不需要为反向设计全新的 kernel 架构——复用和 forward 完全相同的 GEMM 主循环、tiling 策略、TMA 流水线
  - 反向 Epilogue 一定是 tile-local → 一定能融合进转置 GEMM → 一定能享受和 forward 同等的带宽节省
  - 开发者的工作量从"设计 + 实现一个完整的独立 CUDA kernel"降级为"写一个 tile-local 的 VJP 函数"——后者简单得多

**和传统做法对比：**

| | 传统手写融合 | CODA + T1 |
|------|------------|-----------|
| 反向 kernel 架构 | 需要从零设计（内存布局、tiling、流水线全变） | 复用 forward 的 GEMM 主循环模板 |
| 反向融合可行性 | 需要单独论证（每个函数不同） | T1 一劳永逸：只要 forward tile-local，反向一定能融合 |
| 实际要写什么 | 完整的独立 CUDA/Triton kernel | 只写一个 tile-local VJP 函数（几行） |
| FlashAttention 反向 | 等了几个月 | CODA 框架下：写完 forward，反向当天就能跑 |

> **精确定位**：T1 打通的是"前向 tile-local → 反向也一定能写成 GEMM+Epilogue"的**结构保证**，把反向开发从"设计新 kernel 架构"降维为"填空 VJP 函数"。论文中的 LLM 辅助生成（Claude Code 写 `_dswiglu_op`）正是得益于此——LLM 只需要生成 Epilogue 片段，不需要生成整个 kernel。T1 让你从"手艺人雕琢整个算子"变成"手艺人只雕琢 VJP，其余由框架承接"。

### 6.2 RMSNorm 反向 —— Theorem 1 的唯一例外（2 min）

#### 问题：RMSNorm 反向引入了两种跨分块规约

RMSNorm 前向：$h_2 = \text{RMSNorm}(h_1, \gamma) = \frac{h_1}{\text{rms}(h_1)} \odot \gamma$。看似简单的公式，其对 $h_1$ 和 $\gamma$ 的求导却引入了两种需要跨分块通信的规约：

**Problem A：输入梯度需要的行向统计量（Row-wise statistic for $\nabla_{h_1}\mathcal{L}$）**

设连续计算流为 $h_0 = xW_0 \to h_1 = f(h_0) \to h_2 = \text{RMSNorm}(h_1, \gamma) \to y = h_2W_1$。RMSNorm 对输入 $h_1$ 的梯度公式中，包含行向内积统计量：

$$s = \frac{1}{d}\text{sumcols}(\nabla_{h_2}\mathcal{L} \odot h_2)$$

**为什么这打破了 Theorem 1：** 计算 $s$ 需要把 $\nabla_{h_2}\mathcal{L}$ 和 $h_2$ 凑在一起取 Hadamard 积再沿行求和。但在反向传播的数据流中，$\nabla_{h_2}\mathcal{L}$ 是上游梯度经过 $W_1^{\top}$ 才到达的，$h_2$ 是前向保存的中间值——它们不在同一个 GEMM 的寄存器边界上相遇，纯 tile-local 计算拿不到它们。

**Problem B：$\gamma$ 权重梯度需要的跨行特征规约（Feature-wise reduction across rows）**

$$\nabla_{\gamma}\mathcal{L} = \sum_{\text{rows}} \nabla_{h_2}\mathcal{L} \odot \frac{h_1}{\text{rms}(h_1)}$$

需要对整个 batch 中所有 token 的梯度沿行方向累加。这同样是全局规约，不 tile-local。

#### 传统做法

启动独立的 RMSNorm backward kernel → 从 HBM 重新读取（已在前向 Epilogue 中被融合掉、没有单独写回的）$h_1$ 和巨大的 $\nabla_{h_2}\mathcal{L}$ → 分别计算 Problem A 和 Problem B 的规约。这直接打破了 CODA"不往 HBM 写中间结果"的原则，造成了完整的额外 HBM 往返。

#### CODA 的解决方法：代数恒等式 + 两级规约

CODA 对这两个问题分别处理，但核心思想一致——**用代数等价变换把统计量"位移"到数据恰好驻留在寄存器中的 GEMM 边界上。**

---

**Problem A 的解法 —— 恒等变换"位移"统计量**

利用 $\nabla_{h_2}\mathcal{L} = \nabla_{y}\mathcal{L}W_1^{\top}$ 和 $y = h_2W_1$，可以直接证明以下恒等式：

$$s = \frac{1}{d}\text{sumcols}(\nabla_{h_2}\mathcal{L} \odot h_2) = \frac{1}{d}\text{sumcols}(\nabla_y \mathcal{L} \odot y)$$

**硬件含义：** 这个恒等式彻底改变了 $s$ 的计算位置——从需要 $h_2$ 和 $\nabla_{h_2}\mathcal{L}$（两者在反向数据流中位置不同，需要额外 HBM 读取）变成了只需要 $y$ 和 $\nabla_y \mathcal{L}$。而在反向传播执行到产生 $\nabla_{h_2}\mathcal{L}$ 的 GEMM（即 $W_1^{\top}$）时，$y$（前向已经算出来并存着的最终输出）和 $\nabla_y \mathcal{L}$（上游回传的梯度）**恰好同时驻留在当前 GEMM 的寄存器中**。Epilogue 顺手取 Hadamard 积 $\nabla_y \mathcal{L} \odot y$ → 行向累加 → 只把几个标量 $s$ 写回，辅助 kernel 片刻合并。

---

**Problem B 的解法 —— 分块局部规约 + 辅助合并**

对 $\gamma$ 的梯度：在每个 GEMM 的 Epilogue 中计算本地分块的 $\nabla_{h_2}\mathcal{L} \odot \frac{h_1}{\text{rms}(h_1)}$ 局部累加，将分块结果写出 → 微型辅助 kernel 跨所有行合并。

---

**总结：**

| | 传统做法 | CODA |
|------|---------|------|
| Problem A（行向 s） | 独立 kernel 读取 $h_2$ + $\nabla_{h_2}\mathcal{L}$ | 恒等式位移到已有寄存器边界，Epilogue 顺手算 |
| Problem B（$\gamma$ 梯度） | 同上，独立 kernel | 分块局部规约 + 辅助 kernel 合并 |
| HBM 额外读取 | 完整的 $h_2$ 和 $\nabla_{h_2}\mathcal{L}$ 张量 | 仅分块统计量（几个标量） |

**核心哲学：** "不听话"的算子（不 tile-local），用代数恒等式强行让它"听话"——把统计量位移到寄存器就绪的 GEMM 边界。这不是特例的修补方案，而是一个**通用的方法论**：遇到全局规约，先尝试代数等价变换，变换不了再用两级规约。

### 6.3 代码展示 —— 前后向对称的用户 API（1 min）

```python
# coda/kernels/functional/swiglu.py
class LinearSwiGLU(torch.autograd.Function):
    @staticmethod
    def forward(ctx, x, weight):
        pre_act, out = gemm_swiglu(x, weight.mT)  # GEMM + SwiGLU Epilogue
        ctx.save_for_backward(x, weight, pre_act)
        return out

    @staticmethod
    def backward(ctx, dout):
        x, weight, pre_act = ctx.saved_tensors
        grad_pre = dswiglu_backward(pre_act, dout)  # 反向也在 Epilogue 里
        dx = gemm(grad_pre, weight)                  # 标准 GEMM
        dweight = gemm(grad_pre.mT, x)               # 标准 GEMM
        return dx, dweight
```

**关键点：** 前向 `gemm_swiglu` 和反向 `dswiglu_backward` 都是 GEMM + Epilogue 结构。`dswiglu_backward` 虽然是一个单独实现的 VJP 函数（不是编译器自动求导出来的），但它运行在 GEMM 的 Epilogue 中而非作为独立 kernel launch——这正是 Theorem 1 在代码中的直接体现：T1 保证了反向可以写成 GEMM+Epilogue，你只需要填 VJP，不需要设计新 kernel 架构。回顾第 3 节说的"反向必须重新手写完整独立 kernel"的困境，CODA 把它降维成了"手写一个 tile-local VJP"。

### 7.2 LLM 辅助编写：为什么 AI 能写出逼近物理极限的算子（3 min）

#### 传统 LLM 写 CUDA kernel 为什么翻车？

- **搜索空间无限大**：线程块大小、网格大小、共享内存分配、寄存器分配——这些底层参数的组合是天文数字。LLM 盲目去写，经常写出编译报错或性能极差的代码
- **缺乏专家反馈**：一个能榨干 Hopper 性能的 GEMM 主循环，需要顶级硬件专家花费数周甚至数月调优——流水线、双缓冲、TMA 异步搬运的精确编排。LLM 无法无中生有地"发明"这种级别的硬件调度

#### CODA 的解法：从"写整个 kernel"变成"完形填空"

CODA 的核心策略：**不要让 AI 去发明 GEMM 主循环，把最难、最重的硬件调度做成"死模板"，让 AI 只做最后的"尾部填空"。**

1. **固化的执行策略（专家设计的主循环）**：
   - CODA 底层提供由专家千锤百炼、极致优化好的高性能 GEMM 主循环
   - 分块策略、TMA 搬运时序、寄存器分配——全部彻底固化，AI 无法改动、也无需理会

2. **LLM 的任务被降维为原语拼装**：
   - 主循环被框死 → LLM 的工作从"写一个高难度编译器后端"降级为"针对特定 Transformer 计算，从五类原语中选几个，指定拼接顺序"
   - 就像 CODA 已经盖好了钢筋混凝土大楼（GEMM 主循环），LLM 只需要决定房间怎么粉刷（用哪几个 Epilogue 原语、按什么顺序）

3. **精选示例库（Few-Shot / Curated Demonstrations）**：
   - CuTeDSL 太新，LLM 在互联网预训练数据里几乎没见过
   - CODA 团队设计了一个不断扩展的示例库——LLM 看着这些精选示例，**照葫芦画瓢**地改写和重新组合，就能瞬间产出一个全新的高性能 kernel

4. **声明式原语组合**：
   - 开发者（或 LLM）只需要指定原语序列：`[Residual] → [RMSNorm γ] → [SwiGLU]`
   - 库自动将这个组合嵌入固定的专家 GEMM 尾部 → 新的融合 kernel 像搭积木一样组装完成
   - **不需要重写哪怕一行矩阵乘法代码**

| 对比维度 | 含义 |
|---------|------|
| 灰条（Reference Ceiling） | 纯 GEMM、不含任何尾部处理的理论吞吐量上限——任何融合算子都不可能比裸 GEMM 更快 |

**三个关键发现：**

1. **橙条 ≈ 蓝条**：在绝大多数场景（`GEMM-Residual-PartialRMS-GEMM`、`GEMM-RMS-SwiGLU` 等），LLM 生成的算子性能逼近甚至超过人类专家手写——AI 在某些反向传播场景中因为更细粒度的尝试反而略微胜出

2. **橙条 → 灰条**：LLM 生成的融合算子无限逼近纯矩阵乘法的理论物理上限——意味着 Epilogue 的开销几乎被完全隐藏

3. **证明了一套工程范式的可行性**："限定边界 + 原语组合" 这套设计，让 AI 从"大概率写出 bug 和慢代码"变成了"稳定产出高性能算子"。CODA 的作者在论文中使用的正是 Claude Code——不是因为它能写 CUDA，而是因为 CODA 把问题从"写 CUDA"变成了"选原语"

### 8.2 我的实验 —— 融合深度的消融分析（2 min）

## 9. 局限性与思辨（2 min）

- **硬件锁定**：强依赖 Hopper 架构的 TMA 和累加器布局。A100 无 TMA、AMD 无 CUTLASS → 无法直接移植
- **算法局限**：只适用于规整的静态 GEMM。MoE 稀疏路由、动态 Token 丢弃会打破 tile 假设
- **工程门槛**：CuTeDSL 语法晦涩，即使有 LLM 辅助，普通工程师难以维护
- **CODA vs FlashAttention**：不是替代，是互补接力
  - CODA 负责层首尾（投影 + 归一化 + 激活）
  - FA 攻坚中场（Attention + Softmax 全局规约）
  - 两者联手 = 整层 Transformer 只需极少几次 HBM 读写

## 10. 未来展望（1-2 min）

**① 软件与芯片协同设计（Co-Design）：两大趋势**

- **从"手写算子"走向"编译器自动合成"**：以前靠人肉写 CUDA 填补性能瓶颈。CODA 证明"固化 GEMM 核心 + 开放尾部原语"可以让 AI 自动生成硬件级算子。未来算法工程师只需写高层 Python 逻辑，寄存器分配和 TMA 调度由 AI 编译器搞定
- **"以计算换带宽"思想的泛化**：Memory Wall 越来越严重，"万物皆可 GEMM + Epilogue"的设计会扩展到 SSM（Mamba）、扩散模型等非 Transformer 架构

**② 学习路线（给想切入这个领域的同学）**

- 掌握 Hopper/Blackwell 的 TMA 机制和 Tensor Core 累加器布局
- 从 CUTLASS 3.x / CuTe 入手，理解 Layout 和 Copy 机制——这是看懂 CODA 源码的钥匙
- 探索 LLM 辅助编译：将硬件物理约束作为 Prompt 输入代码模型，让 AI 替代人类做高性能算子微调

**③ 三个高落地价值的工业场景**

- **万卡大规模训练**：微小算子延迟累加起来是百万美元级的算力浪费。CODA 适合部署在 Llama-3、Mixtral 等 SwiGLU/RMSNorm 结构的大模型训练框架中
- **端侧设备**：手机 NPU/边缘 GPU 带宽极低但计算单元充沛 → CODA 的零拷贝片上闭环天然匹配端侧推理和 LoRA 微调
- **定制化 ASIC 生态**：国产 GPU 最大痛点是"没生态，每个算子都要手写"。CODA 的"固化 GEMM + 原语自动组合"提供了完美模板——芯片厂商只需固化自己的 GEMM，算子层交给这套体系

**④ 我的思考：DiT 才是更值得的方向**

> Transformer 已被 FlashAttention、Liger Kernel 等手写算子榨干到 90% 以上。CODA 在 Transformer 上只是"锦上添花"。而 DiT（扩散 Transformer）正处于"空有强大架构，极度缺乏系统级融合优化"的荒芜期——AdaLN 调制、时间步注入等胶水算子占 30-40% 耗时。设计 AdaLN-Epilogue 原语 + 多步去噪上下文片上常驻机制，将 CODA 推广至 DiT 多步推理，有望实现 1.5×-2× 的端到端加速。
