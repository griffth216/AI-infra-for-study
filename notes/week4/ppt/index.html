前向融合走得越远，反向传播就越痛苦——为 Theorem 1 做铺垫。
§3 · WHY TRADITIONAL FUSION FAILS
08 / 37
核心论点 · 为 Theorem 1 做铺垫

前向融合 ≠ 反向能用

左 · 三个根本原因
① 数学公式变了：前向 SwiGLU f(x)=silu(x_g)⊙x_u → 反向含 sigmoid 导数、指数、乘法链路——完全不同的计算。
② 前向省掉的中间结果，反向又要回来：要么妥协写回（打破融合初衷），要么重计算（增加逻辑复杂度）。
③ 内存对齐全乱了：前向按行读取 → 反向转置后按列读取，合并访存被破坏。
右 · 手写融合的工程代价
前向手工写一套 CUDA/Triton kernel → 反向必须原封不动再受一遍苦。
FlashAttention 的教训：前向出来几个月后反向才出来——同一个团队、同一个算子，只是方向反了。
底部结论："前向 GEMM + Epilogue" 如果不能让反向自动继承，就没有从根本上解决问题。

§5.1 · GEMM-RESIDUAL-RMSNORM-GEMM
12 / 37
SCENE · FORMULA · TRADITIONAL · DEFECT

GEMM-Residual-RMSNorm-GEMM 模式

5.1
场景
残差 → RMSNorm → 下一个 GEMM 的"三明治"，跨越两个 GEMM，Transformer 中出现 3 处：Attention输出→残差→RMSNorm→MLP门控 ／ MLP降级→残差→RMSNorm→QKV ／ 最终MLP→残差→RMSNorm→LM Head
核心公式
y = RMSNorm(xW₀+z, γ)W₁ = (r(xW₀+z)⊙γ)W₁
传统计算过程（4 步，每一步都是一次 HBM 往返）
① GEMM1：算 h₀ = xW₀ → 写回 HBM
② 从 HBM 读回 h₀ → 算 h₀+z → 算 RMSNorm（需要全局平方和，所有线程阻塞等待标量 r）
③ 用 r 缩放后 → 写回 HBM
④ 从 HBM 读回 → GEMM2
致命缺陷
两个 GEMM 被 RMSNorm 的全局同步硬生生阻断——GPU 大量时间在等。瓶颈不在计算，在 r 需要隐藏维度（d=4096~8192）上的全局平方和。残差加和 ×γ 本是 tile-local，但 r 不 tile-local。
§5.1 · CODA SOLUTION · 三步编排 + 延迟缩放
13 / 37
CODA RESTRUCTURING · 代数重构：r 推迟到 GEMM2 尾部应用

CODA 重构：三步编排 + 延迟缩放

STEP 1 · GEMM1 + EPILOGUE1
h₀=xW₀ → h₁=h₀+z（残差加，Elementwise Map）→ h₂=h₁⊙γ（Vector Load 广播）→ partialRMS(h₁²)（Tile Reduction，每tile产出一个标量）
STEP 2 · 微型辅助 KERNEL
合并 ~32 个局部标量 → 得全局 r。输入量从 O(D) 降为 O(num_tiles)。辅助 kernel 极轻量（几微秒），只读几十个标量。
STEP 3 · GEMM2 + EPILOGUE2
h₃=h₂W₁（此时不需要 r，直接开始算！）→ y[i,j]=r[i]·h₃[i,j]（最后才乘 r）。代数trick：数乘结合律让 GEMM2 不必等待 r。
# 代数证明：数乘结合律 y = (r(xW₀+z)⊙γ)W₁ = r((xW₀+z)⊙γ)W₁ ← r 是标量，提取到最外层 # 两级规约之和等于全局和 Σ_{i=1}^{D} u_i² = Σ_{tiles} Σ_{i∈tile} u_i²
💡 与 5.2/5.3 的关键区别：此模式跨越两个 GEMM，不能单次 kernel launch → 拆成三步编排。5.2/5.3 是单 GEMM 内 compose() 搞定。每个步骤内部仍是 GEMM+Epilogue 结构。
# ops.py — 三步编排（每个 step 都是 GEMM+Epilogue） def gemm_residual_rmsnorm_gemm_fwd(x, y, w_a, w_b, w_n, ...): # Step 1: GEMM1 + Residual + ×γ + 局部平方和 x_out, s, h = gemm_residual_partial_rmsnorm( A=y, B=w_a, C=x, W=w_n, ...) # Step 2: 微型辅助规约 → 全局 r rstd_out = compute_rstd(s=s, eps=eps) # Step 3: GEMM2 + 延迟缩放（r 在 Epilogue 中应用） z_out = gemm_rmsnorm(A=h, B=w_b, R=rstd_out) return x_out, y_out, z_out, rstd_out
优化结果传统CODA
GEMM 间的同步等待必须等 r 算完零等待，r 延迟到 GEMM2 尾部
RMSNorm 开销独立 kernel，读整行求平方和两级规约：局部算 + 辅助合并
辅助规约输入量O(D)（完整张量）O(num_tiles)（~32 个标量）

Pairwise Activations 模式：SwiGLU / RoPE

5.2
场景
单 GEMM 内配对：MLP 门控 SwiGLU（降维，Gate+Up→1输出）／注意力 RoPE（保维，2D旋转变换）——GEMM 产出的两半在尾部需原地配对
核心公式
h = xW,　ha[i,j],hb[i,j] = split(h[i,j]),　y[i,j] = f(ha[i,j],hb[i,j])　（SwiGLU: f(g,u)=silu(g)⊙u 降维 | RoPE: 2D旋转 保维）
传统计算过程
① GEMM 算出膨胀中间矩阵 H（SwiGLU 需 gate+up 2倍宽度，D→2D）→ 完整写回 HBM（FP16 下可达数百 MB）
② 启动独立激活 kernel → 从 HBM 重新读取 H
③ 跨半个矩阵拉取配对元素 h_a[j] 和 h_b[j]（物理距离 = D，cache miss严重）
④ 算完 → 再次写回 HBM
致命缺陷
中间膨胀矩阵两次完整 HBM 往返。配对元素物理距离远（h_a 在矩阵前半，h_b 在后半），独立激活 kernel 需要跨 D 列拉取数据 → cache miss 严重。Kernel launch 开销叠加。
两种典型 Pairwise 激活
SwiGLU（降维 N→N/2）：Gate 通道负责"开关"，Up 通道负责"信号"。f(g,u)=silu(g)⊙u。需 2× 宽度的中间矩阵。
RoPE（保维 N→N）：对相邻两个通道做 2D 旋转：f(x₂ₖ,x₂ₖ₊₁)=(x₂ₖcosθ−x₂ₖ₊₁sinθ, x₂ₖsinθ+x₂ₖ₊₁cosθ)。Q 和 K 各需一次。
共性：每个输出元素只依赖固定相邻的两个输入元素——完美 tile-local，不需要跨块通信。

CODA RESTRUCTURING · 算法层→硬件层→闭环

CODA 重构：权重列交错重排 + 累加器布局闭环

① 算法层 · 权重列交错重排（离线，一次性）：W=[W_a,0,...,W_b,0,...] → W_int=[W_a,0, W_b,0, W_a,1, W_b,1,...]。ha[j] 和 hb[j] 从相隔 D 列 → 物理相邻（2j 和 2j+1）。代数证明：矩阵乘法每列独立，列重排只改变布局不改变结果。
② 硬件层 · Hopper 累加器布局暴露（全文最关键的一条硬件依赖）：Hopper 在 Epilogue 阶段向程序员暴露 Tensor Core 累加器物理分布——相邻输出元素天然、必然落在同一线程寄存器中。⚠ 消费级显卡或不开放累加器布局的架构上，此优势被直接击穿。
③ 闭环：算法重排使配对元素物理相邻 → Hopper 保证相邻元素同线程同寄存器 → 线程一低头，恰好是需要配对的两个数 → 直接应用 f，零显存交通，零跨线程通信。

SCENE · FORMULA · TRADITIONAL · DEFECT

Cross-Entropy Loss 模式

5.3
场景
LM Head 巨型词表（V ≥ 32K，LLaMA-3 为 128K）Cross-Entropy Loss——单 GEMM + 微型辅助 kernel。Online Softmax（Stateful Transform）进入 Epilogue，不写回完整 Logits。
核心公式
Logits = X · W_lm ∈ ℝ^{B×L×V}
ℓ = −logits[y] + LSE(logits)
B=2, L=4096, V=32000 → FP16 中间张量 ≈ 500MB
传统计算过程
① GEMM 算出 B×L×V 的完整 Logits 矩阵（batch=2, seq=4096, V=32000 → FP16 约 500MB）
② 完整写回 HBM——训练中最大的单次 HBM 写入
③ 启动独立 Softmax/Loss kernel → 从 HBM 重新读出完整 Logits → 算 LSE → 算 loss
④ 中间 Logits 矩阵占据了巨大显存，随词表增长极易 OOM
致命缺陷
纯访存瓶颈——Logits 是训练中最大的中间张量之一。500MB 往返对 HBM 带宽是巨大的浪费。
§5.3 · CODA SOLUTION · Online Softmax + 微型辅助
17 / 37
CODA RESTRUCTURING · 500MB Logits → 几 KB 统计量

CODA 重构：Online Softmax 分块统计 + 辅助规约

STEP 1 · GEMM 分块产出
每次产出 256 个 logits（仍驻留寄存器），不写回 HBM。分块遍历整个词表维度 V。
STEP 2 · EPILOGUE 原地处理
每个 tile 都做：Stateful Transform 维护 running m, l（Online Softmax），不管 target 在不在本块——全局 LSE 需要所有块的 (m_t, s_t)。额外检查：target label y_i 是否在本块覆盖的词表范围内 → 如果是，额外寄存 h_i,y_i（用于最终的 −logits[y] 项）。每个 tile 只写回几个标量到 HBM。
STEP 3 · 微型辅助 KERNEL 合并
合并所有 tile 的 local max/sum-exp → 全局 LSE → 代入公式得 ℓ_i。输入仅几 KB，微秒级完成。
# 代数证明：Online Softmax 精确递推（无近似） m_global = max_t m_t s_global = Σ_t s_t · exp(m_t − m_global) logΣexp(h) = m_global + log(s_global) # 与 Week 1 学的 Online Softmax 同一思想
分块统计量可以精确合并成全局 LSE。递推公式是精确的，没有任何数值近似。虽然 kernel launch 数没减少（仍是 2），但第二个 kernel 的输入从 500MB→几KB，I/O 量差了 5 个数量级。
优化结果传统CODA
HBM 写入量完整 Logits（500MB-1GB）分块统计量（总计几 KB）
显存占用随词表增长极易 OOM近乎为零（不保存 Logits）
HBM 读取Softmax kernel 重新读完整 Logits辅助 kernel 只读几 KB

§6.1 · THEOREM 1 · 最简模型推导
19 / 37
SCENE · FORMULA · TRADITIONAL · 前向→反向三步推导

Theorem 1 场景：前向融合 ≠ 反向可用

核心公式 · 最简模型（一个激活函数 f 隔开两个 GEMM）
前向：h = xW₀, h' = f(h), y = h'W₁
f 是逐元素激活（ReLU/GeLU/SiLU），每个位置的输出只依赖同位置的输入——tile-local。
传统困境 · 反向为什么痛苦？
① 数学公式变了（SwiGLU前向简单，反向含sigmoid导数、指数、乘法链）
② 前向省掉的中间结果，反向又要回来
③ 数据流方向反了，内存对齐全乱了（前向行主序→反向列主序）
→ 反向必须原封不动再受一遍手写kernel的苦（FlashAttention反向等了几个月）
链式法则推导（已知 ∇yL，求三层梯度）
① ∇h'L = ∇yL·W₁ᵀ — 标准 GEMM ② ∇hL = ∇h'L ⊙ f'(h) — 逐元素 Hadamard 积（tile-local） ③ ∇xL = ∇hL·W₀ᵀ — 标准 GEMM
关键观察 · 结构完全对称
Step 1Step 2Step 3
前向GEMM(W₀)f(h)GEMM(W₁)
反向GEMM(W₁ᵀ)⊙f'(h)GEMM(W₀ᵀ)
前向反向完全同一拓扑：GEMM → tile-local 变换 → GEMM。唯一区别是融合方向：前向 f 在 W₀ 的 Epilogue（前融），反向 ⊙f'(h) 在 W₀ᵀ 的 Epilogue（后融）。

Theorem 1：雅可比分块对角 ⇒ 反向 tile-local

# 前向（L-1个GEMM-Epilogue块 + 最终GEMM） h_ℓ = x_{ℓ-1}W_ℓ, x_ℓ[i,j] = f_ℓ[i,j](h_ℓ[i,j]) ℓ=1..L-1 h_L = x_{L-1}W_L # Theorem 1：反向保持完全相同的结构 ∇x_{ℓ-1}L = ∇h_ℓL·W_ℓᵀ # 标准 GEMM ∇h_{ℓ-1}L[i,j] = g_{ℓ-1}[i,j](∇x_{ℓ-1}L[i,j], h_{ℓ-1}[i,j]) # tile-local Epilogue ∇W_ℓL = x_{ℓ-1}ᵀ∇h_ℓL # 权重梯度（独立GEMM）
雅可比证明直觉：f_ℓ[i,j] 仅依赖当前分块 [i,j] → 全矩阵雅可比 ∂x_ℓ/∂h_ℓ 是分块对角矩阵 → 转置也是分块对角 → g_ℓ 天然 tile-local → 反向没有引入任何新的跨分块通信。计算 ∇h_{ℓ-1}L[i,j] 所需的所有材料，天然就在当前 GEMM 的寄存器里。

§6.2 · RMSNORM BACKWARD · Theorem 1 的例外
22 / 37
SCENE · FORMULA · TRADITIONAL · 两种打破 T1 的跨分块规约

RMSNorm 反向：Theorem 1 的唯一例外

— 场景 & 公式 / 连续计算流
h₀=xW₀ → h₁=f(h₀) → h₂=RMSNorm(h₁,γ) = (h₁/rms(h₁))⊙γ → y=h₂W₁
RMSNorm 看似简单的行向归一化，其对 h₁ 和 γ 的求导却引入了两种需要跨分块通信的规约，打破了 T1 的 tile-local 前提。
— Problem A / 行向统计量 s
s = (1/d)·sumcols(∇h₂L ⊙ h₂)
需把 ∇h₂L（经 W₁ᵀ 到达）和 h₂（前向保存）凑在一起取 Hadamard 积再行向求和——两者不在同一 GEMM 寄存器边界上相遇，纯 tile-local 拿不到。
— Problem B / γ 权重梯度
∇γL = Σ_rows ∇h₂L ⊙ h₁/rms(h₁)
需要跨 batch 所有 token 沿行方向累加——同样是全局规约，不 tile-local。
— ✕ / 传统做法
启动独立 RMSNorm backward kernel → 从 HBM 重新读取（已在 Epilogue 中处理过的）h₁ 和巨大的 ∇h₂L → 分别计算两个规约 → 打破 CODA "零中间张量"原则。解法见下一页。
§6.2 · CODA SOLUTIONS · 恒等变换 + 两级规约
23 / 37
CODA RESTRUCTURING · 让不听话的算子"听话"

CODA 解法：恒等变换 + 两级规约

PROBLEM A 解法 · 恒等变换"位移"统计量
s = (1/d)·sumcols(∇h₂L ⊙ h₂) = (1/d)·sumcols(∇yL ⊙ y) ← 恒等式！
利用 ∇h₂L=∇yL·W₁ᵀ 和 y=h₂W₁。硬件含义：y 和 ∇yL 在反向 GEMM（W₁ᵀ）执行时恰好同时驻留在寄存中 → Epilogue 顺手取 Hadamard 积 → 行向累加 → 只写回几个标量 s。不需要额外读取 h₂ 和 ∇h₂L。
PROBLEM B 解法 · 分块局部规约 + 辅助合并
每个 GEMM 的 Epilogue 算本地分块的 ∇h₂L ⊙ h₁/rms(h₁) 局部累加 → 写出分块结果 → 微型辅助 kernel 跨行合并。与 §5.1 的两级规约是同一套模式。
优化结果传统CODA
Problem A（行向 s）独立 kernel 读取 h₂ + ∇h₂L恒等式位移到寄存器边界，Epilogue 顺手算
Problem B（γ 梯度）同上，独立 kernel分块局部规约 + 辅助 kernel 合并
HBM 额外读取完整 h₂ 和 ∇h₂L 张量仅分块统计量（几个标量）
💡 核心哲学：遇到全局规约 → 先尝试代数等价变换（把统计量"位移"到数据恰好在寄存器中的 GEMM 边界上）→ 变换不了再用两级规约（局部归约 + 辅助 kernel 合并）。这是通用方法论，不是特例修补。

代码：前后向对称 GEMM+Epilogue API

# coda/kernels/functional/swiglu.py class LinearSwiGLU(torch.autograd.Function): @staticmethod def forward(ctx, x, weight): pre_act, out = gemm_swiglu(x, weight.mT) # GEMM + SwiGLU Epilogue ctx.save_for_backward(x, weight, pre_act) return out @staticmethod def backward(ctx, dout): x, weight, pre_act = ctx.saved_tensors grad_pre = dswiglu_backward(pre_act, dout) # ← VJP 也跑在 Epilogue 里 dx = gemm(grad_pre, weight) # 标准 GEMM dweight = gemm(grad_pre.mT, x) # 标准 GEMM return dx, dweight
对称结构：前向 gemm_swiglu 和反向 dswiglu_backward 都是 GEMM + Epilogue 结构。dswiglu_backward 虽单独实现，但跑在 GEMM Epilogue 中而非独立 kernel launch。
Theorem 1 的工程价值：T1 保证了反向一定可以写成 GEMM+Epilogue → 不需要为反向设计新 kernel 架构 → 复用 forward 的 GEMM 主循环、tiling策略、TMA流水线。
回顾 §3 的困境：反向必须重新手写完整独立 kernel（FlashAttention 反向等了几个月）→ CODA + T1 把反向开发从"设计新 kernel 架构"降维为"填空 VJP 函数"——几行代码即可。
