## 1. 实验定位：将论文的隐式设计决策显式量化

### 论文的"黄金融合方案"已经摆在那里

回头看论文图 2 的底行——那个融合块边界不是随便画的：

```
[QKV Proj + Scale + RoPE]  →  Attention  →  [Out Proj + Partial Norm + Residual]
                                                  ↓
                                            [Gate/Up Proj + SwiGLU]
```

融合块之间被 **Attention（Softmax 全局规约）** 和 **Reduction（All-Reduce 跨卡同步）** 硬性隔开。不是作者不想继续融合，而是这两类操作天然打破 tile-locality——一个需要跨序列位置求全局 softmax 分母，一个需要跨 GPU 同步梯度。

**融合块的边界 = tile-locality 被打破的物理边界。** 论文作者通过工程直觉找到了这个最优停损点，但他们没有把"为什么停在这"的权衡逻辑用数据显式地画出来。

### 本实验做什么

不是"发现论文没发现的东西"，而是**把作者通过工程师直觉已经做对的决策，用一条"融合深度 → 加速比"曲线显式验证一遍**：

- 论文说"融合到跨 tile 通信为止"是对的，我们拿数据证明为什么不能继续往下融
- 笔记中反复讨论的"省带宽 vs 寄存器压力"的权衡，我们把它画成一条可读的曲线
- 汇报时说"论文的融合方案背后有一套隐式的设计原则，我设计实验把这个原则量化了出来"

## 2. 实验方法：反证法

不追求精确控制融合深度（那需要 CuTeDSL/Triton），而是反过来——每个深度同时跑两版代码，差值就是融合收益：

| 版本 | 实现方式 | 含义 |
|------|---------|------|
| 融合版 (Fused) | `@torch.compile` 自动融合 | "编译器能帮你省多少" |
| 未融合版 (Unfused) | PyTorch eager mode | "如果不融合要花多少" |

**为什么用 eager mode 而非 `.contiguous()`？**

GEMM (`x @ w`) 的输出天然是 contiguous 的 stride 张量。在 contiguous 张量上调 `.contiguous()` 是 PyTorch 的显式 no-op——它检测到已经是 contiguous，直接返回同一个 tensor，**不会插入任何 kernel launch**，因此无法打断融合。

Eager mode 则不同：`h = x @ w` 是一个 kernel，`h = h + residual` 是另一个 kernel。没有 `torch.compile` 的图捕获，PyTorch 不会跨 op 边界做融合，每个 op 独立 launch → 独立写回 HBM。这才是真正的"未融合"基线。

**验证方法：** 对 eager 版跑一次 `torch.profiler.profile()`，在 chrome trace 里数 kernel 数量 = op 数量，确认每个 op 之间有明确的 kernel boundary。

## 3. 实验矩阵

| 深度 | 操作链 | eager kernel 数（估算） | 模拟什么 |
|------|--------|------------------------|---------|
| L0 | `x @ w` | 1 | 纯 GEMM——吞吐量理论上限 |
| L1 | `x @ w + residual` | 2 | GEMM + 残差连接 |
| L2 | L1 → RMSNorm（含 γ 缩放） | ~5-6 | Attention 输出 → 残差 → Norm |
| L3 | L2 + SwiGLU（gate/up GEMM + silu × gate） | ~8-10 | 完整 MLP 块前向 |
| L4 | L3 + RoPE（cos/sin 旋转） | ~10-12 | QKV 投影 + 位置编码 |

**共享配置：**
- M = N = K = 4096（模拟 7B 级别模型的单层隐藏维度）
- dtype = `torch.bfloat16`
- 设备 = `cuda`
- Warmup = 30 次，Benchmark = 100 次
- 取中位数（median）而非均值（避免 GPU 偶发抖动污染）

## 4. 代码实现

### 4.1 通用工具函数

```python
import torch
import torch.utils.benchmark as benchmark

DEVICE = "cuda"
DTYPE = torch.bfloat16
M, N, K = 4096, 4096, 4096
WARMUP = 30
REPEATS = 100

def benchmark_fn(fn, name, warmup=WARMUP, repeats=REPEATS):
    """跑 warmup + repeats，返回中位延迟 (ms)"""
    # warmup
    for _ in range(warmup):
        fn()
    torch.cuda.synchronize()

    # benchmark with CUDA events
    start = torch.cuda.Event(enable_timing=True)
    end = torch.cuda.Event(enable_timing=True)
    timings = []
    for _ in range(repeats):
        start.record()
        fn()
        end.record()
        torch.cuda.synchronize()
        timings.append(start.elapsed_time(end))

    median_ms = sorted(timings)[len(timings) // 2]
    print(f"  {name:20s}: {median_ms:.4f} ms")
    return median_ms
```

### 4.2 输入生成

```python
def make_inputs(m=M, n=N, k=K):
    x = torch.randn(m, k, device=DEVICE, dtype=DTYPE)
    w = torch.randn(k, n, device=DEVICE, dtype=DTYPE)
    residual = torch.randn(m, n, device=DEVICE, dtype=DTYPE)

    # RMSNorm weight (向量, 维度 n)
    gamma = torch.randn(n, device=DEVICE, dtype=DTYPE)

    # SwiGLU 权重: gate/up 合并 (K x 2N)
    w_gate_up = torch.randn(n, 2 * n, device=DEVICE, dtype=DTYPE)

    # RoPE 的 cos/sin 表
    cos = torch.randn(m, n, device=DEVICE, dtype=DTYPE)
    sin = torch.randn(m, n, device=DEVICE, dtype=DTYPE)

    return x, w, residual, gamma, w_gate_up, cos, sin
```

### 4.3 各深度的 eager 版（未融合基线）

```python
# ===== L0: 纯 GEMM =====
def eager_l0(x, w):
    return x @ w

# ===== L1: GEMM + Residual =====
def eager_l1(x, w, residual):
    h = x @ w           # kernel 1: cuBLAS GEMM
    h = h + residual    # kernel 2: element-wise add
    return h

# ===== L2: GEMM + Residual + RMSNorm (γ 缩放) =====
def eager_l2(x, w, residual, gamma, eps=1e-6):
    h = x @ w                           # kernel 1: GEMM
    h = h + residual                    # kernel 2: add
    h_sq = h ** 2                       # kernel 3: square
    var = torch.mean(h_sq, dim=-1, keepdim=True)  # kernel 4: reduction
    rstd = 1.0 / torch.sqrt(var + eps)  # kernel 5: rsqrt
    h = h * rstd                        # kernel 6: scale
    h = h * gamma                       # kernel 7: γ broadcast
    return h

# ===== L3: L2 + SwiGLU =====
# SwiGLU(x) = silu(x @ W_gate) * (x @ W_up)
# 这里用合并权重 W_gateup = [W_gate | W_up], 先做 GEMM 再 split
def eager_l3(x, w, residual, gamma, w_gate_up, eps=1e-6):
    # Step 1: L2 阶段 (GEMM + Residual + RMSNorm)
    h = x @ w
    h = h + residual
    h_sq = h ** 2
    var = torch.mean(h_sq, dim=-1, keepdim=True)
    rstd = 1.0 / torch.sqrt(var + eps)
    h_norm = h * rstd * gamma

    # Step 2: SwiGLU
    gate_up = h_norm @ w_gate_up        # kernel: GEMM (MxN × Nx2N → Mx2N)
    gate, up = gate_up.chunk(2, dim=-1) # kernel: split (可能是 view, 零开销)
    # silu(x) = x * sigmoid(x)
    activated = gate * torch.sigmoid(gate)  # kernel: silu
    out = activated * up                    # kernel: element-wise multiply
    return out

# ===== L4: L3 + RoPE =====
def eager_l4(x, w, residual, gamma, w_gate_up, cos, sin, eps=1e-6):
    # Step 1-2: 同 L3
    h = x @ w
    h = h + residual
    h_sq = h ** 2
    var = torch.mean(h_sq, dim=-1, keepdim=True)
    rstd = 1.0 / torch.sqrt(var + eps)
    h_norm = h * rstd * gamma

    gate_up = h_norm @ w_gate_up
    gate, up = gate_up.chunk(2, dim=-1)
    activated = gate * torch.sigmoid(gate)
    out = activated * up

    # Step 3: RoPE (旋转位置编码)
    # 将相邻维度配对做 2D 旋转
    out_2d = out.view(out.shape[0], -1, 2)        # reshape: 相邻两个值成一对
    out_rot = torch.empty_like(out_2d)
    out_rot[..., 0] = out_2d[..., 0] * cos - out_2d[..., 1] * sin
    out_rot[..., 1] = out_2d[..., 0] * sin + out_2d[..., 1] * cos
    return out_rot.view_as(out)
```

### 4.4 各深度的 `torch.compile` 版（融合版）

```python
# compile 版就是 eager 版代码加 @torch.compile 装饰
# 注意：torch.compile 首次调用会触发编译，warmup 阶段会吸收这个开销

@torch.compile
def fused_l0(x, w):
    return x @ w

@torch.compile
def fused_l1(x, w, residual):
    h = x @ w
    h = h + residual
    return h

@torch.compile
def fused_l2(x, w, residual, gamma, eps=1e-6):
    h = x @ w
    h = h + residual
    h_sq = h ** 2
    var = torch.mean(h_sq, dim=-1, keepdim=True)
    rstd = 1.0 / torch.sqrt(var + eps)
    h = h * rstd
    h = h * gamma
    return h

@torch.compile
def fused_l3(x, w, residual, gamma, w_gate_up, eps=1e-6):
    h = x @ w
    h = h + residual
    h_sq = h ** 2
    var = torch.mean(h_sq, dim=-1, keepdim=True)
    rstd = 1.0 / torch.sqrt(var + eps)
    h_norm = h * rstd * gamma
    gate_up = h_norm @ w_gate_up
    gate, up = gate_up.chunk(2, dim=-1)
    return gate * torch.sigmoid(gate) * up

@torch.compile
def fused_l4(x, w, residual, gamma, w_gate_up, cos, sin, eps=1e-6):
    h = x @ w
    h = h + residual
    h_sq = h ** 2
    var = torch.mean(h_sq, dim=-1, keepdim=True)
    rstd = 1.0 / torch.sqrt(var + eps)
    h_norm = h * rstd * gamma
    gate_up = h_norm @ w_gate_up
    gate, up = gate_up.chunk(2, dim=-1)
    out = gate * torch.sigmoid(gate) * up
    out_2d = out.view(out.shape[0], -1, 2)
    out_rot = torch.empty_like(out_2d)
    out_rot[..., 0] = out_2d[..., 0] * cos - out_2d[..., 1] * sin
    out_rot[..., 1] = out_2d[..., 0] * sin + out_2d[..., 1] * cos
    return out_rot.view_as(out)
```

### 4.5 主循环

```python
def run_experiment():
    x, w, residual, gamma, w_gate_up, cos, sin = make_inputs()

    depths = ["L0", "L1", "L2", "L3", "L4"]
    results = {d: {"eager_ms": 0.0, "fused_ms": 0.0} for d in depths}

    # --- L0 ---
    results["L0"]["eager_ms"] = benchmark_fn(
        lambda: eager_l0(x, w), "L0 eager")
    results["L0"]["fused_ms"] = benchmark_fn(
        lambda: fused_l0(x, w), "L0 fused")

    # --- L1 ---
    results["L1"]["eager_ms"] = benchmark_fn(
        lambda: eager_l1(x, w, residual), "L1 eager")
    results["L1"]["fused_ms"] = benchmark_fn(
        lambda: fused_l1(x, w, residual), "L1 fused")

    # --- L2 ---
    results["L2"]["eager_ms"] = benchmark_fn(
        lambda: eager_l2(x, w, residual, gamma), "L2 eager")
    results["L2"]["fused_ms"] = benchmark_fn(
        lambda: fused_l2(x, w, residual, gamma), "L2 fused")

    # --- L3 ---
    results["L3"]["eager_ms"] = benchmark_fn(
        lambda: eager_l3(x, w, residual, gamma, w_gate_up), "L3 eager")
    results["L3"]["fused_ms"] = benchmark_fn(
        lambda: fused_l3(x, w, residual, gamma, w_gate_up), "L3 fused")

    # --- L4 ---
    results["L4"]["eager_ms"] = benchmark_fn(
        lambda: eager_l4(x, w, residual, gamma, w_gate_up, cos, sin), "L4 eager")
    results["L4"]["fused_ms"] = benchmark_fn(
        lambda: fused_l4(x, w, residual, gamma, w_gate_up, cos, sin), "L4 fused")

    # --- 汇总 ---
    print("\n" + "=" * 60)
    print(f"{'Depth':<8} {'Eager (ms)':<15} {'Fused (ms)':<15} {'Speedup':<10} {'Reduction':<10}")
    print("-" * 60)
    for d in depths:
        e = results[d]["eager_ms"]
        f = results[d]["fused_ms"]
        speedup = e / f
        reduction = (e - f) / e * 100  # 延迟减少百分比
        print(f"{d:<8} {e:<15.4f} {f:<15.4f} {speedup:<10.2f}x {reduction:<10.1f}%")
    print("=" * 60)

    return results

if __name__ == "__main__":
    run_experiment()
```

## 5. Kernel Launch 数量验证（Profiler）

在单独的验证脚本中跑（不在主 benchmark 循环里，因为 profiler 本身有开销）：

```python
import torch

# 对 eager 版 L2 做 profiling
x, w, residual, gamma, _, _, _ = make_inputs()

with torch.profiler.profile(
    activities=[torch.profiler.ProfilerActivity.CPU, torch.profiler.ProfilerActivity.CUDA],
    record_shapes=True,
) as prof:
    eager_l2(x, w, residual, gamma)
    torch.cuda.synchronize()

print(prof.key_averages().table(sort_by="cuda_time_total", row_limit=15))

# 对 fused 版 L2 同样做
with torch.profiler.profile(
    activities=[torch.profiler.ProfilerActivity.CPU, torch.profiler.ProfilerActivity.CUDA],
    record_shapes=True,
) as prof:
    fused_l2(x, w, residual, gamma)
    torch.cuda.synchronize()

print(prof.key_averages().table(sort_by="cuda_time_total", row_limit=15))
```

**重点关注：** profiler 输出中 CUDA kernel 行的数量。
- eager L2：应看到 7 行左右（对应 7 个 op）
- fused L2：可能只有 1-3 行（GEMM + fused elementwise）
- 这个差异就是融合效果的直观证据

## 6. 预期结果与图表

### 与论文图 2 的对照关系

实验结果不应孤立地看，而应该**映射回论文图 2 的融合块边界**：

```
论文图 2 底行:
[QKV Proj + Scale + RoPE]  →  Attention  →  [Out Proj + Partial Norm + Residual]
    ↑ L4 对应此处                      ↑ L3 对应此处              ↑ L2 对应此处
    (融合了 RoPE)                      (无法融合:               (融合了 Norm + Residual)
                                       全局 Softmax)

                                [Gate/Up Proj + SwiGLU]
                                    ↑ L3 也对应此处
                                    (融合了 Gated Activation)
```

我们的 L0-L4 本质上是**沿着论文的融合块，从"裸 GEMM"逐步叠加 Epilogue 直到逼近下一个 tile-locality 边界**。当曲线在某个深度增速骤降时，那个拐点就应该对应论文图 2 中某个融合块的边界。

### 图 1：延迟对比柱状图（Fused vs Unfused）

```
         Eager (unfused)    Fused (torch.compile)
         ████████████       ██████
L0       ████████████  1.0x ██████
L1       ██████████████ 1.2x ██████
L2       ██████████████████ 2.0x █████████
L3       ██████████████████████████ 3.0x ██████████
L4       ██████████████████████████████ 3.2x ███████████
         └─ kernel 数量多 ─┘       └─ kernel 少，但单 kernel 越来越重 ┘
```

**预期趋势：**
- L0→L1：加速比 ≈ 1.0-2.0×（只融合一个 element-wise add，收益有限）
- L1→L2：加速比跳升（RMSNorm 的 reduction 被融合，省去一次 HBM 往返）
- L2→L3：加速比继续增长（SwiGLU 的膨胀中间矩阵被融合，收益大）
- L3→L4：加速比增长放缓甚至持平（RoPE 虽然融合了，但寄存器压力开始显现）

**关键观察点：** L3→L4 如果加速比增长明显放缓，说明开始触碰融合的物理边界。

### 图 2：Kernel Launch 数量对比

```
Depth    Eager kernels    Fused kernels    Reduction
L0       1                1                0%
L1       2                1-2              0-50%
L2       7                2-3              57-71%
L3       10-12            2-4              60-80%
L4       12-15            3-5              60-75%
```

**预期趋势：** fused 版的 kernel 数远小于 eager，且随深度增长缓慢——验证了 compile 确实在融合。

### 图 3：双 Y 轴合成图 —— "黄金融合点"

- Y1 轴（柱状图）：加速比（eager latency / fused latency）
- Y2 轴（折线）：fused 版的 kernel launch 数
- X 轴：融合深度 L0 → L4
- **标注论文图 2 的融合块边界**：在曲线拐点处画一条竖虚线，标注 "论文图 2 的融合边界"

**关键叙事：** 曲线拐点恰好落在论文图 2 融合块的边界上。不是作者不想继续融（比如把 Attention 也融进去），而是 Softmax 的全局规约天然打破 tile-locality——从我们的数据可以清晰看到：**到这个深度之后，编译器已经无法继续减少 kernel launch 数了，继续叠加 Epilogue 原语只会让单 kernel 越来越重而不再减少 HBM 往返。** 论文作者通过工程直觉做出了正确的停损决策，我们用数据把它显式化了。

## 8. 风险与应对

| 风险 | 概率 | 应对 |
|------|------|------|
| `torch.compile` 在某些 depth 上不触发融合 | 中 | 用 profiler 验证 kernel 数是否确实减少。如果 L3/L4 融合效果差，反而说明融合深度的确有物理边界——这在汇报中可以作为一个观察点 |
| BF16 在 RTX 4060 上精度不同 | 低 | 4060 支持 BF16（Ada Lovelace 架构）。如果不支持，降级为 FP16 |
| Profiler 在 Windows 上无法导出 chrome trace | 中 | Chrome trace 是加分项不是必需项。`key_averages().table()` 的文本输出已经足够作为证据 |
| L4 的 eager 版 OOM | 低 | M=N=K=4096 的中间张量约 64MB（BF16），RTX 4060 8GB 绰绰有余 |
