## 第一部分：这周学了什么（4 分钟）

### GPU 的存储系统不是一个平面，是四层金字塔

这周系统学习了 GPU 的存储层次结构。GPU 的存储系统不是一块统一的内存，而是从上到下四层。用一个工厂车间的类比来理解：

| 层 | 容量（参考 A100） | 速度 | 类比 | 存什么 |
|---|---|---|---|---|
| **寄存器** | 256KB / SM | 0 cycle | 工人手心里的纸条 | 当前正在算的那几个数 |
| **共享内存/SRAM** | 192KB / SM | ~20 cycles | 小组眼前的工作台 | 这一组工人共用的一小块数据 |
| **L2 Cache** | 40MB / 全卡 | ~200 cycles | 车间公共货架 | 各组都可能用到的共享物料 |
| **HBM/显存** | 80GB / 全卡 | ~600 cycles | 园区外的大仓库 | 全部模型参数、所有中间结果 |

> 一句话总结：越往上越快但越小，越往下越大但越慢。

这不是设计偏好，是物理约束——SRAM 一个 bit 占的芯片面积是 DRAM 的 5-7 倍。如果把 80GB 全换成片上 SRAM，芯片面积要 16000mm²，一片 12 寸晶圆只能切三四颗，物理上没意义。快和大在硅基芯片上无法兼得，所以必须分层。

### 重点学了两层：HBM 和 SRAM

**HBM — 大仓库，靠"加车道"而不是"踩油门"提速**

传统显存（GDDR）像平房，内存颗粒平铺在 PCB 板上，数据通道 32-64 根，要提速就得拉高频率 → 功耗爆炸。HBM 像摩天大楼，多层 DRAM 芯片垂直堆叠，通过 TSV（硅通孔）贯通各层，数据通道 1024 根。它不靠提高频率，靠增加并行通道。代价是贵——数据中心卡用 HBM 一张十几万，消费级用 GDDR 一张几千块。

**SRAM — 工作台，程序员手动管理**

SRAM 和 L2 都是片上缓存，但有个本质区别：L2 由硬件自动管理，程序员控制不了数据什么时候被换出；SRAM 完全由程序员在代码里用 `__shared__` 手动控制——什么时候搬数据、搬多少、什么时候释放。这是 AI Infra 工程师优化算子的核心抓手。同时 SRAM 有一个坑：硬件上被分成 32 个 Bank，32 个线程同时访问同一个 Bank 会排队串行（Bank Conflict），性能暴跌。优化时经常用 Padding 来规避——比如声明 `[32][32+1]` 故意多一列，让每行元素错开到不同 Bank。

### 还了解了一个硬件趋势

SRAM 每代涨 25-33%（A100 192KB → H100 256KB/SM）。HBM 带宽从 A100 的 2TB/s 涨到了 B200 的 8TB/s，涨了 4 倍——但同期算力涨了 7 倍。矛盾没消失，只是一起往前平移。

> 顺带一提：上周学 FlashAttention 时反复出现的"从 HBM 搬进 SRAM"、"阅后即焚"这些概念，这周学完存储层次之后完全理解了——本质就是把数据放在 SRAM（20 cycles）上算，而不是在 HBM（600 cycles）上反复读写。

## 第二部分：发现了什么问题（4 分钟）

### 问题一：算力过剩，带宽不足——"内存墙"

以我的 RTX 4060 为例算一笔账：

```
GPU 算力（FP16 Tensor Core）：  121 TFLOPS  =  每秒 121 万亿次运算
HBM 带宽（GDDR6）：              272 GB/s   =  每秒 2720 亿字节

每个 FP16 数据占 2 字节 → 每秒最多搬 1360 亿个数字进来
121 万亿 ÷ 1360 亿 ≈ 889

意味着：从 HBM 每读一个数字，需要对这个数字做 889 次运算，才能"喂饱" GPU
但 LLM 推理（Decode 阶段）通常一个数字只做 1-2 次运算
→ GPU 的实际算力利用率不到 0.2%
```

这不是 RTX 4060 的问题。A100 同样面临这个矛盾：312 TFLOPS ÷ 2TB/s ≈ 156 FLOPS/Byte，H100 更极端：989 TFLOPS ÷ 3.35TB/s ≈ 295 FLOPS/Byte。算力涨得比带宽快，这个矛盾是 GPU 架构与生俱来的。

### 问题二：SRAM 太小了

```
A100 的 SRAM（工作台）： 约 20 MB
A100 的 HBM（大仓库）： 80 GB

工作台只有大仓库的 0.025%
但几乎所有计算都必须在工作台上完成——数据不搬上来就算不了
```

这就像一个流水线工人，工作台只有巴掌大，原料全在几百米外的大仓库。绝大多数时间花在"取料"上，不是"加工"上。

### 问题三：HBM 容量涨不过模型规模

```
2020 年：A100 → 80GB   |   GPT-3 → 175B 参数
2024 年：H200 → 141GB  |   GPT-4 → ~1.7T 参数
2025 年：B200 → 192GB  |   下一代 → 估计 10T+ 参数
```

模型规模涨了 ~60 倍，显存容量只涨了 2.4 倍。差距不是在缩小，是在拉大。

### 三个问题的共同根源

**数据和算力不在同一个地方。** 数据在 HBM（慢但大），算力在 SM（快但只能用小数据）。搬数据的时间远大于算数据的时间。

## 第三部分：这些问题怎么被解决的（4 分钟）

### 核心思路：既然搬数据是瓶颈，那就少搬

标准 Attention 的做法是：先算出完整的 N×N 注意力分数矩阵（约 128MB，N=4096 时），整个存在 HBM 里，再读出来做 Softmax，再读出来乘 V。每一步都是 HBM 级的读写（600 cycles/次）。

FlashAttention 的思路是：**这个大矩阵根本不需要完整存在 HBM 里。** 把它切成小块，每次只搬一小块到 SRAM 里计算，算完直接扔，不写回 HBM。

```
标准做法：HBM 存完整的 N×N 矩阵 → 读出来 softmax → 写回去 → 读出来乘 V → 写回去
         HBM 读写量：O(N²) — 毁灭性的

FlashAttention：切成小块 → 每块在 SRAM 里完成全部计算 → 只把很小的最终结果写回 HBM
         HBM 读写量：O(N) — 和序列长度线性增长
```

计算量一点没少，SRAM 本身也没变快。**快在哪里？快在少跑了仓库。**

### block_size 怎么定的？— 一个具体的例子

```
SRAM 容量 = 128 KB（RTX 4060 每 SM）
每次搬进来：Q 块 + K 块 + V 块 + 临时 S 矩阵

block_size = 64：  Q[64,64] + K[64,64] + V[64,64] + S[64,64]
                   8KB + 8KB + 8KB + 8KB = 33KB ✓ 安全

block_size = 128： Q[128,64]+K[128,64]+V[128,64]+S[128,128]
                   16+16+16+32 = 80KB，已经有点紧了

block_size = 256： S[256,256] = 128KB 光这一个就快爆了
                   总计 > 224KB ✗ 直接溢出
```

这就是 block_size 不能随便设大的原因——它是被 SRAM 的物理容量卡死的。以及为什么 H100 的 SRAM 从 192KB 涨到 256KB 能让 FlashAttention 天然更快——分块可以设得更大，总搬运次数更少。

### 这个案例说明了什么

FlashAttention 不是一个数学创新——它的数学公式和标准 Attention 完全等价。它是一个**硬件调度创新**：在硬件不变的前提下，重新设计数据的搬运路线，让同样的计算少跑几十倍的 IO。这就是"IO-Aware 算法"的含义。这也是 AI Infra 这个方向的核心方法论——不是造更快的硬件，不是发明更"聪明"的模型结构，而是在理解硬件约束后，找到更优的计算编排方式。

## 第四部分：当前还有哪些问题，大家在怎么优化（3 分钟）

FlashAttention 解决了一个问题，但它不是终点。围绕 GPU 存储层次，当前有两个核心瓶颈正在被活跃攻克。

### 瓶颈一：SRAM 太小，卡住了分块算法的上限

**为什么是问题**：从第三部分的 block_size 算例能直接看到——block_size 能设多大，完全取决于 SRAM 有多大。SRAM 每代只涨 25-33%（A100 192KB → H100 256KB/SM），因为一个 SRAM bit 占的面积是 DRAM 的 5-7 倍，芯片总面积是硬约束，只要还用硅和 6T SRAM cell 就不可能暴涨。

**当前怎么优化**：

- **硬件侧 — TMA（Tensor Memory Accelerator）**：H100 新增的硬件单元，专门加速数据从 HBM 到 SRAM 的异步搬运。它不能增大 SRAM，但能让搬运更高效——原来需要线程们协作搬数据（占线程、占指令），TMA 在后台自己搬，线程腾出手来专心计算。FlashAttention-3 就是充分利用了 TMA 才实现了进一步加速。

- **软件侧 — 编译器自动分块（Autotuning）**：Triton 等编译器开始做自动搜索——程序员只写计算逻辑，编译器自动尝试不同 block_size，找到最优的 SRAM 分配方案。这解决了"每个 GPU 的 SRAM 大小不同，block_size 要手动重新算"的问题。

### 瓶颈二：HBM 带宽不够，Memory-bound 问题不会自动消失

**为什么是问题**：第二部分算过——B200 的 HBM3e 带宽 8 TB/s，但算力 2250 TFLOPS，要求每个 byte 做 281 次运算才喂饱 GPU。而 Decode 阶段每个 byte 只做 1-2 次运算。HBM 带宽从 A100 的 2TB/s 涨到 B200 的 8TB/s，涨了 4 倍——但算力涨了 7 倍。**矛盾不是缩小了，是更大了。**

**当前怎么优化**：

- **HBM4（预计 2026-2027）**：位宽从 1024-bit 翻倍到 2048-bit，单 stack 带宽 6-8+ TB/s，堆叠 16 层。但功耗和散热是巨大挑战——B200 已经 1000W 了，HBM4 只会更高。

- **近存计算（Processing-in-Memory / PIM）**：一个更根本的思路——在 HBM 堆栈内部加入简单的处理单元，让一部分计算直接在内存侧完成，从根本上减少搬数据的需求。三星和 SK 海力士都在推，但目前成熟度还不高，编程模型也不完善。

- **低精度计算**：FP8 → FP4 → INT4。把数据精度砍一半，等效带宽翻倍。B200 已经支持 FP4，这是短期内见效最快、成本最低的方向。缺点是精度损失，不是所有任务都能用。

### 学完这两周，我的理解

> 来课题组之前，我以为 AI 训练和推理慢是因为 GPU 算得不够快。学完这两周我意识到，瓶颈不在算力，在搬运。GPU 每年算力涨 50%+，但数据搬进来的速度只涨 30%——算力越强，这个矛盾越尖锐。
>
> 当前业界的优化可以分成两条路：**硬件侧微调比例**（HBM4、更大 L2、近存计算）和**软件侧重写 IO 模式**（FlashAttention、Triton 编译器、低精度计算）。前者每代给 30-50% 的提升，后者一次可以给 10-100×。AI Infra 这个方向之所以有吸引力，就是因为在软件侧还有巨大的空间可以挖掘。
>
> 这也是我想继续深入的方向——不是在硬件和算法之间做选择，而是理解两者的约束后，找到让它们更好配合的方式。
