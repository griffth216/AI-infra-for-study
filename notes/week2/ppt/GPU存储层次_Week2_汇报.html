GPU 存储系统：四层金字塔
GPU 的存储不是一个平面，而是从上到下四层结构。越上层越快但越小，越下层越大但越慢 — 这是物理约束，不是设计偏好。
① 寄存器（Register File）
每 SM 256 KB，由 65,536 个 32-bit 寄存器组成。位于 ALU 旁边，~0 cycle 延迟。线程私有，编译器自动分配。寄存器溢出（Register Spilling）到 HBM 是性能杀手。每线程最多 255 个寄存器，寄存器用量直接决定 SM 占用率（Occupancy）。
② 共享内存 / SRAM
每 SM 192 KB（A100），与 L1 Cache 共享同一块片上 SRAM 物理资源，延迟 ~20 cycles。由程序员通过 __shared__ 手动管理。核心用途：分块计算（Tiling）减少 HBM 访问、线程间通信、数据重组。硬件上分为 32 个 Bank，需小心 Bank Conflict。
③ L2 Cache
全卡 40 MB（A100），所有 SM 共享，延迟 ~200 cycles。由硬件自动管理（LRU 替换策略），程序员不可直接控制。A100 支持 L2 Residency Control，可将部分数据永久锁定在 L2 中。带宽 ~4 TB/s，是 HBM 的 2 倍。PagedAttention 的分块设计有利于提升 L2 命中率。
④ HBM / 显存
全卡 80 GB（A100），基于 3D 堆叠 DRAM + TSV（硅通孔）技术，延迟 ~600 cycles。位宽 1024-bit（HBM3e），靠增加并行通道而非提高频率来提升带宽。存放全部模型参数、中间激活值和 KV Cache。从 A100 的 2.0 TB/s 到 B200 的 8.0 TB/s，带宽每代提升 ~50–70%。
物理约束：SRAM 一个 bit 需要 6 个晶体管（6T cell），芯片面积是 DRAM（1T1C cell）的 5–7 倍。如果把 80 GB HBM 全换成片上 SRAM，芯片面积将达到 ~16,640 mm²，一片 12 寸晶圆只能切 3–4 颗。快和大在硅基芯片上无法兼得，必须分层。
HBM：靠「加车道」提速，而非「踩油门」
传统 GDDR 与 HBM 的架构对比 — 平房 vs 摩天大楼
GDDR — 传统显存
"平房"：内存颗粒平铺在 PCB 板上
位宽32–64 bit
提速方式提高频率 → 功耗爆炸
典型带宽272 GB/s（RTX 4060）
价格消费级，整机 ~¥7,000
封装PCB 平面布局，颗粒散布在 GPU 周围
HBM — 高带宽内存
"摩天大楼"：多层 DRAM 垂直堆叠 + TSV 贯通
位宽1024 bit（HBM3e），HBM4 → 2048 bit
提速方式增加并行通道，低频低压
典型带宽2.0 TB/s（A100）→ 8.0 TB/s（B200）
价格数据中心级，单卡 ~¥100,000
封装3D 堆叠 + 硅中介层，TSV 微米级铜柱互连
关键洞察：HBM 不靠提高频率，靠增加并行通道。代价是贵 — 数据中心卡用 HBM（单卡十几万），消费级用 GDDR（单卡几千块）。但"内存墙"（算力增速远超带宽增速，计算单元大量时间空等数据）只是被推远了，核心矛盾并未消失。
SRAM 结构原理：为什么切成 32 个 Bank？
物理上 SRAM 与 L1 Cache 共享同一块片上 SRAM（A100: 192 KB/SM），程序员可配置分配比例
为什么要切成 Bank？
SRAM 使用 6T SRAM cell，每周期只能提供 一个读写端口。如果整块 SRAM 是一个整体，一个 Warp 的 32 个线程只能串行访问 → 32 个周期才能服务完一次请求。

解决方案：将 SRAM 硬件上切分为 32 个等大的 Bank，每个 Bank 有独立的读写端口。32 个线程同时访问 32 个不同 Bank → 1 个周期全部完成，吞吐量 ×32。
Bank 编址方式
以 4 字节（32-bit word） 为单位交错编址：

Bank = (byte_addr / 4) % 32

地址 0–3 (word 0) → Bank 0
地址 4–7 (word 1) → Bank 1
…
地址 124–127 (word 31) → Bank 31
地址 128–131 (word 32) → Bank 0（循环回来）
Bank Conflict — 当多个线程撞上同一个 Bank
定义：同一 Warp 内，n 个线程访问同一 Bank 的不同地址 → 硬件将这 n 个请求串行化，需要 n 个周期完成。
特例 — 广播（不冲突）：多个线程访问完全相同的地址 → 硬件检测到后广播给所有线程，1 个周期完成。
通用判定公式：gcd(32, stride) > 1 → 有 Bank Conflict
只有 stride 为奇数时（gcd=1）一定无冲突。
stride = 1（连续）→ 无冲突
T0→Bank0, T1→Bank1, …, T31→Bank31
stride = 2 → 2 路冲突
T0→Bank0, T1→Bank2, …
T16→word32→Bank0 与 T0 冲突！
stride = 32 → 32 路冲突（最坏）
全部 32 线程命中 Bank 0
Padding 解法 — 数学原理与二维数组的 Bank 映射
二维数组的行优先存储：C/C++ 中 tile[R][C] 在内存中按行连续排列。元素 tile[row][col] 的线性地址为：
word_index = row × C + col → Bank = (row × C + col) % 32
不 Padding：C = 32
Bank = (row × 32 + col) % 32 = col % 32
→ Bank 号与 row 无关，只取决于 col。所有 32 行的同一列全部命中同一个 Bank → 32 路冲突。
Padding：C = 32 + 1 = 33
Bank = (row × 33 + col) % 32
∵ 33 ≡ 1 (mod 32) ∴ row × 33 ≡ row (mod 32)
→ Bank = (row + col) % 32 Bank 号随行号线性偏移。
为什么能消除冲突？列访问时 col 固定，Bank = (row + col) % 32。row 从 0 递增到 31，Bank 号依次取 col, col+1, col+2, …, col+31 (mod 32) — 恰好遍历全部 32 个 Bank，每个线程命中不同 Bank，零冲突。

代价：每行浪费 1 个元素（4 字节），32 行共浪费 128 字节。换来 32 路冲突 → 1 路（无冲突），性能改善 5%–35%。

核心技巧：选择 C 使得 gcd(C, 32) = 1（互质）。33 与 32 互质，同理 31、35、37 等奇数均可。33 最常用是因为只浪费 1/32 ≈ 3% 的空间。

SRAM 应用一：分块计算（Tiling）
SRAM 装不下整个矩阵 → 切成 Tile 分批算 → 每个元素只从 HBM 读一次
问题：数据复用被 HBM 带宽吞掉了
矩阵乘 C[M,N] = A[M,K] × B[K,N]（M=N=K=4096）。A 的同一行被 N 个线程各读一次，B 的同一列被 M 个线程各读一次。每个 FP16 元素 2 字节，A 被读 N 次、B 被读 M 次 → 总共 ~4096³ × 2 ≈ ~136 GB HBM 流量。计算量仅 ~137 GFLOPS → Arithmetic Intensity ≈ 1 → 严重 Memory-bound。99.8% 的时间计算单元在等数据。
↓ SRAM 解决方案 ↓
解决：Tile = 线程共享的工作台，每个元素只搬一次
将 A、B 切成 Tile（如 32×32）。Block 内所有线程协作把 A 的当前 Tile 从 HBM 搬进 SRAM，同样搬 B 的 Tile。在 SRAM 上完成部分积后循环到下一个 Tile。A 的每个元素只从 HBM 读 1 次（而非 N/32 次），同一 Block 线程通过 SRAM 共享。HBM 流量缩减 30–100×，Arithmetic Intensity 从 ~1 升至 ~30+，从 Memory-bound 转为 Compute-bound。
FlashAttention 就是 Tiling：block_size 即 Tile 尺寸。Q 块锁定在 SRAM，内层循环换入新 K、V 块覆盖同一块 SRAM（"阅后即焚"），HBM 搬运从 O(N²) 降到 O(N)。
SRAM 应用二：线程间通信 + 同步
线程的中间结果互相依赖 → 需要共享空间交换数据 → SRAM 是唯一低延迟选择
问题：寄存器私有、HBM 太慢，线程间无法高效共享中间结果
并行归约（Parallel Reduction）：Block 内 256 线程各自算局部和，然后两两合并（256→128→64→…→2→1）。每一轮合并，线程 A 必须读到线程 B 刚算出的值。寄存器是线程私有的（A 看不到 B 的寄存器），HBM 延迟 600 cycles 太慢。如果走 HBM，每一步归约等 600 cycles → 8 轮归约 = 4800 cycles → 归约成为整个算子的瓶颈。
↓ SRAM 解决方案 ↓
解决：SRAM 当共享黑板 + __syncthreads() 当集合哨
① 各线程将局部和写入 SRAM（sdata[tid] = mySum）
② __syncthreads() — 轻量级 Barrier（~20 cycles），确保所有线程写完才继续
③ 线程从 SRAM 读对方的局部和，相加，写回 SRAM
④ 重复 ②③ 直到归约完成
效果：整个归约在 SRAM 内完成，HBM 零参与。__syncthreads() 保证"先写后读"的因果顺序，消除数据竞争。SRAM 20 cycles 延迟 vs HBM 600 cycles → 归约速度提升 30×。
延伸：Softmax 的 max 统计、LayerNorm 的均值/方差、FlashAttention 中跨线程共享 Q 块 — 全部依赖这套 SRAM + Barrier 机制。
SRAM 应用三：数据重组 — 挽救非合并访问
HBM 只在连续访问时快 → 乱序数据先搬进 SRAM → 重排后再连续写回
问题：HBM 要求连续访问，乱序数据性能暴跌至 1/32
HBM 的 Cache Line 为 128 字节（连续 32 个 FP32）。一个 Warp 的 32 个线程必须访问连续对齐的 128 字节，HBM 控制器才能用 1 个事务完成全部读取。如果线程访问分散地址（stride 访问、AoS 结构体、稀疏索引 gather）→ 每个线程触发独立 HBM 事务 → 32 个事务 → 带宽利用率仅 1/32。常见场景：AoS→SoA 转换、图像转置（行存→列读）、稀疏矩阵的 gather/scatter、图神经网络邻居采样。
↓ SRAM 解决方案 ↓
解决：三步"搬→排→写"，SRAM 作为排序缓冲区
SRAM 的随机访问不经过 L2/HBM 的 Cache Line 机制，stride 访问仅 20 cycles。
① 搬进（Gather）— 线程用合并访问把一整段原始数据从 HBM 搬进 SRAM（连续读，带宽跑满）
② 重排（Reorder）— 在 SRAM 内按目标顺序重新排列（20 cycles 随机访问，零 HBM 开销）
③ 写回（Scatter）— 重排后的连续数据以合并访问写回 HBM
本质：用 SRAM 的低延迟随机访问能力，吸收"非合并→合并"的格式转换成本，让 HBM 始终以峰值带宽读写。
常见应用：图像转置预处理、AoS→SoA 布局转换、稀疏矩阵解压重排、FlashAttention 中 Kᵀ（转置）在 SRAM 内完成不触发 HBM 读写。

FlashAttention 不是数学创新，是硬件调度创新 — "IO-Aware 算法"的含义
✕ 标准 Attention
① 算出完整 N×N 注意力矩阵（~128 MB, N=4096）
② 整个存在 HBM 里
③ 读出来做 Softmax → 写回 HBM
④ 读出来乘 V → 写回 HBM
⑤ 每一步都是 HBM 级读写（600 cycles/次）
HBM 读写量：O(N²) — 毁灭性的
✓ FlashAttention
① 切成小块，每次只搬一小块到 SRAM
② 在 SRAM 里完成 Q×Kᵀ → Softmax → ×V
③ 算完直接扔，不写回 HBM
④ 只把很小的最终结果 O 写回 HBM
⑤ 大部分操作在 SRAM（20 cycles）完成
HBM 读写量：O(N) — 线性增长
关键洞察：计算量一点没少，SRAM 本身也没变快。快在哪里？快在少跑了仓库。这就是 "IO-Aware 算法" 的含义 — 在硬件不变的前提下，重新设计数据的搬运路线，让同样的计算少跑几十倍的 IO。这也是 AI Infra 这个方向的核心方法论：不是造更快的硬件，不是发明更"聪明"的模型结构，而是在理解硬件约束后，找到更优的计算编排方式。

当前瓶颈一：SRAM 太小，卡住分块算法上限
一个 SRAM bit = 6 个晶体管（6T cell），面积是 DRAM 的 5–7 倍，物理上限无法突破
为什么是问题
· block_size 能设多大，完全取决于 SRAM 有多大
· SRAM 每代只涨 25–33%（A100 192KB → H100 256KB/SM）
· 根本原因：6T SRAM cell 占面积是 DRAM 的 5–7×
· 芯片总面积是硬约束，只要还用硅和 6T SRAM cell 就不可能暴涨
软件侧 — 编译器自动分块（Autotuning）
Triton 等编译器开始做自动搜索 — 程序员只写计算逻辑，编译器自动尝试不同 block_size，为每个 GPU 找到最优 SRAM 分配方案。解决了"每个 GPU 的 SRAM 大小不同，block_size 要手动重新算"的痛点。
硬件侧 — TMA（Tensor Memory Accelerator）
H100 新增的硬件单元，专门加速数据从 HBM 到 SRAM 的异步搬运。它不能增大 SRAM，但能让搬运更高效 — 原来需要线程们协作搬数据（占线程、占指令），TMA 在后台自己搬，线程腾出手来专心计算。FlashAttention-3 就是充分利用了 TMA 才实现了进一步加速。
过渡：SRAM 的瓶颈导致了分块算法有理论上限。但这不是唯一的瓶颈 — HBM 带宽的不足同样致命，且矛盾在加剧。
当前瓶颈二：HBM 带宽不够 — 三条优化路线并行
Memory-bound 问题不会自动消失 — B200 算力涨 7×，带宽只涨 4×，矛盾加剧
路线一：HBM4（硬件侧微调比例）
方向：位宽从 1024-bit 翻倍到 2048-bit，单 stack 带宽 6–8+ TB/s，堆叠 16 层 DRAM。预计 2026–2027 年落地。

挑战：功耗和散热是巨大瓶颈 — B200 已经 1,000W 了，HBM4 只会更高。每代给 30–50% 的提升，但无法从根本上解决矛盾。
路线二：近存计算 PIM（架构重构）
方向：在 HBM 堆栈内部加入简单处理单元，让一部分计算直接在内存侧完成，从根本上减少搬数据需求。三星、SK 海力士均在推进。

挑战：成熟度不高，编程模型不完善。目前尚处于早期阶段。
路线三：低精度计算（软件侧压缩）
方向：FP8 → FP4 → INT4，把数据精度砍一半，等效带宽翻倍。B200 已支持 FP4。这是短期见效最快、成本最低的方向。

挑战：精度损失不可避免，不是所有任务都能用低精度。
两条路并行：硬件侧微调比例（HBM4、更大 L2、近存计算）→ 每代 +30–50% 的提升；软件侧重写 IO 模式（FlashAttention、Triton 编译器、低精度计算）→ 一次可以给 10–100× 的提升。AI Infra 的价值就在这里 — 不是在硬件和算法之间做选择，而是理解两者的约束后找到让它们更好配合的方式。
