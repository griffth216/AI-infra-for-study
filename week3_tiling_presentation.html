FlashAttention — Tiling 在 Attention 中的示范

标准 Attention 的中间结果 S = QKᵀ 和 P = softmax(S) 都是 O(N²)，N=8192 时达 256 MB，全写回 HBM。

# FlashAttention: 不存 S 和 P，把 Q,K,V 切成小块
# 外层循环 (K/V blocks), 内层循环 (Q blocks)
for Kj, Vj in K_blocks, V_blocks:
    load Kj, Vj from HBM → SRAM
    for Qi in Q_blocks:
        load Qi from HBM → SRAM
        Sij = Qi × Kj^T        # on SRAM, NOT written back
        Pij = softmax(Sij)      # on SRAM, NOT written back
        Oi += Pij × Vj          # accumulate on SRAM
    # only O written back to HBM
共同的核心

数据切块 → 片上计算 → 中间结果不写回 HBM → 省 O(N²) 带宽。这就是 tiling + 片上数据复用。

第三章

Naive GEMM — 逐行分析 GPU 上发生了什么

__global__ void sgemm_naive(
    const float* __restrict__ A,  // M×K, row-major
    const float* __restrict__ B,  // K×N, row-major
    float* __restrict__ C,        // M×N
    int M, int N, int K
) {
    int row = blockIdx.y * blockDim.y + threadIdx.y;
    int col = blockIdx.x * blockDim.x + threadIdx.x;
    if (row >= M || col >= N) return;

    float acc = 0.0f;
    for (int k = 0; k < K; k++) {
        // 每次迭代：2 次 Global Memory 读 (~760 cycles) + 1 次 FMA (~1 cycle)
        acc += A[row * K + k]    // ← Global Memory，~380 cycles
             * B[k * N + col];   // ← Global Memory，~380 cycles
    }
    C[row * N + col] = acc;
}
跟踪一个线程，计算 C[0][0]

迭代 k=0: 读 A[0][0] + B[0][0] → 760 cyc 等数据，1 cyc 计算

迭代 k=1: 读 A[0][1] + B[1][0] → 又是 760 cyc 等数据

...

算力利用率 ≈ 1/761 ≈ 0.13%

实际有 L1/L2 cache 和 warp 调度帮忙，不会这么惨，但本质是 memory-bound。

A[row*K+k] — 连续地址 → coalesced ✓

B[k*N+col] — stride = N×4B → 无法合并 ✗

第三章

从"全体数据"看 Naive GEMM 的浪费

A[0][0] 这个元素被读了几次？

  • 线程(0,0) 读它，算 C[0][0]
  • 线程(0,1) 读它，算 C[0][1]
  • 线程(0,2) 读它，算 C[0][2]
  • ...
  • 线程(0, N-1) 读它，算 C[0][N-1]

A[0][0] 被 N 个线程各读了一次 = 被读了 N 次！

同理 B[0][0] 被 M 个线程各读了一次。

M=N=K=4096 时数值
总计算量2 × 4096³ ≈ 137 GFLOP
总访存量 (worst, 无 cache)≈ 512 GB
算术强度0.27 FLOP/Byte
RTX 4060 需要的强度 (FP32)55.5 FLOP/Byte
差距≈ 200×
根本原因

GPU 每秒能算 15.1×10¹² 次浮点运算，每秒只能从显存搬 272×10⁹ 字节。每读一个字节必须做 55.5 次浮点运算 才能不让算力空转。Naive GEMM 每次读一个字节只做 0.27 次运算 — 算力在疯狂等数据。

Tiling 算法

怎么切、怎么算 — 把矩阵切成 TILE×TILE 小块，搬到 Shared Memory 再算
第四章

Tiling 核心思路

矩阵太大 → 切成小块 (Tiles) → 每次只搬一块到 Shared Memory → 在 Shared Memory 上把这一块能做的计算都做完 → 再换下一块。

C[i][j] = Σk A[i][k] × B[k][j]

把 K 维切成 K/TILE 段。例如 C₀₀ = A₀₀·B₀₀ + A₀₁·B₁₀ + A₀₂·B₂₀

关键收益

A 的每个元素从 HBM 读入次数: N 次 → N/TILE 次

减少倍数 = TILE_SIZE。算术强度 = naive × TILE_SIZE

 矩阵 A (M×K)              矩阵 B (K×N)              矩阵 C (M×N)
 ┌─────────────────┐      ┌─────────────────┐      ┌─────────────────┐
 │ A₀₀ │ A₀₁ │ A₀₂ │      │ B₀₀ │ B₀₁ │ B₀₂ │      │ C₀₀ │ C₀₁ │ C₀₂ │

 │ A₁₀ │ A₁₁ │ A₁₂ │      │ B₁₀ │ B₁₁ │ B₁₂ │      │ C₁₀ │ C₁₁ │ C₁₂ │
 │─────┼─────┼─────│      │─────┼─────┼─────│      │─────┼─────┼─────│
 │ A₂₀ │ A₂₁ │ A₂₂ │      │ B₂₀ │ B₂₁ │ B₂₂ │      │ C₂₀ │ C₂₁ │ C₂₂ │

 每个子块: TILE×TILE

 C₀₀ = A₀₀·B₀₀ + A₀₁·B₁₀ + A₀₂·B₂₀
          ↑ 第 0 个 tile pair       ↑ 第 1 个           ↑ 第 2 个

 沿 K 维循环 K/TILE 次，每次:
   1. 把 A tile 和 B tile 从 HBM 搬进 Shared Memory (各搬 1 次)
   2. Shared Memory 上算完这个 tile 对 C 的贡献 (~20 cyc/读)
   3. 累加进 Register 的 acc

第四章

Tiled GEMM Kernel — 完整代码

#define TILE 32

__global__ void sgemm_tiled(
    const float* __restrict__ A,   // M × K, row-major
    const float* __restrict__ B,   // K × N, row-major
    float* __restrict__ C,         // M × N, row-major
    int M, int N, int K
) {
    // Step 1: Shared Memory — SRAM 上分配，Block 内所有线程共享
    // TILE×TILE = 1024 float = 4KB, 两个 tile = 8KB (48KB 限制内)
    __shared__ float As[TILE][TILE];
    __shared__ float Bs[TILE][TILE];

    // Step 2: 每个线程负责 C 的一个元素
    int row = blockIdx.y * TILE + threadIdx.y;
    int col = blockIdx.x * TILE + threadIdx.x;
    float acc = 0.0f;  // ← 累加器在 Register (~1 cycle)

    int num_tiles = (K + TILE - 1) / TILE;

    // Step 3: 沿 K 维遍历所有 tile pairs
    for (int t = 0; t < num_tiles; t++) {

        // 3a. 协作加载 A tile (1024 线程各搬 1 个 → 并行完成)
        int a_col = t * TILE + threadIdx.x;
        As[threadIdx.y][threadIdx.x] =
            (row < M && a_col < K) ? A[row * K + a_col] : 0.0f;

        // 3b. 协作加载 B tile
        int b_row = t * TILE + threadIdx.y;
        Bs[threadIdx.y][threadIdx.x] =
            (b_row < K && col < N) ? B[b_row * N + col] : 0.0f;

        // 3c. Barrier 1: "所有人都加载完了"
        __syncthreads();

        // 3d. Shared Memory 上累加 (~20 cyc/读, 不是 ~400)
        for (int k = 0; k < TILE; k++)
            acc += As[threadIdx.y][k] * Bs[k][threadIdx.x];

        // 3e. Barrier 2: "所有人都用完了, 可以覆盖了"
        __syncthreads();
    }

    // Step 4: 写回 Global Memory
    if (row < M && col < N) C[row * N + col] = acc;
}
L1: __shared__

物理在 SM 的 SRAM，整个 Block (1024 线程) 共享一份。

L3a-b: 协作加载

每个线程用唯一的 (threadIdx.y, threadIdx.x) 索引加载 A tile 的一个元素。1024 个 load 并行发出，感知延迟 ≈ 1 次 load。

L3c: __syncthreads() #1

"数据搬完了才能开始算" — 防止快线程读到慢线程还没写完的旧数据。

L3d: 内层累加

As[ty][k]: A tile 同一行不同列。Bs[k][tx]: B tile 同一列不同行。数据在 Shared Memory，~20 cyc vs ~400 cyc。

L3e: __syncthreads() #2

"数据用完了才能覆盖" — 防止快线程在慢线程还在读的时候写入下一轮的新数据。

第四章

两个 __syncthreads() — 为什么一个都不能少

Barrier 1 — 去掉后的后果
场景：2 个线程 (简化)，TILE=2。线程 0 加载慢 (还在等 Global Memory)，线程 1 加载快已经进入累加循环。
结果：线程 1 读到的 As[0][0] 是线程 0 还没写完的旧值/半写值 → C 算错。
Barrier 2 — 去掉后的后果
场景：线程 0 算得快，已进入下一轮循环 (t+1)，开始把新 A tile 写入 As[0][0]。线程 1 算得慢，还在读 As[0][0] 做累加。
结果：线程 1 读到的是一半旧数据 + 一半新数据的混合 → C 混入了下一轮的数据。 
for (int t = 0; t < num_tiles; t++) {
    // ═══ Phase A: Load (Global → Shared) ═══
    As[threadIdx.y][threadIdx.x] = A[row * K + a_col];
    Bs[threadIdx.y][threadIdx.x] = B[b_row * N + col];

    __syncthreads();
    //      ↑ ALL threads MUST reach here before proceeding
    //      "所有人数据都搬完了，Shared Memory 现在完整安全"

    // ═══ Phase B: Compute (Shared → Register) ═══
    for (int k = 0; k < TILE; k++)
        acc += As[threadIdx.y][k] * Bs[k][threadIdx.x];

    __syncthreads();
    //      ↑ ALL threads MUST finish reading before overwrite
    //      "所有人都用完了当前 tile，可以安全覆盖"
}
本质

两个 barrier 定义了一段临界区：Shared Memory 在 Load 完成 → Compute 完成之间是只读的。

第四章

协作加载 — 为什么 1024 线程各搬一个

方案机制感知延迟
A: 协作加载1024 线程各执行 1 次 Global Load≈ 1× load 延迟
B: 单线程循环1 线程执行 1024 次 Global Load1024 × 400 ≈ 390K cyc
GPU 延迟隐藏的核心

1024 个 load 请求同时发出 — 虽然每个都要等几百 cycles，但时间窗口重叠，感知延迟 ≈ 一次 load。

同一 warp 的 32 线程访问连续地址 → 硬件 合并为一次事务 (coalescing)。

// ---- 协作加载 A tile ----
// 问题: A tile 有 TILE×TILE = 1024 个 float 需要加载
// 答案: Block 里有 1024 个线程，每个加载一个
//       (threadIdx.y, threadIdx.x) 对每个线程唯一

int a_col = t * TILE + threadIdx.x;
//  ↑ 当前 A tile 内的全局列号 (0..K-1)

As[threadIdx.y][threadIdx.x] =              // Shared Memory 对应位置
    (row < M && a_col < K)                   // 边界检查
    ? A[row * K + a_col]                     // row 固定 (线程全局行)
    : 0.0f;                                  // 越界填 0

// ---- 协作加载 B tile ----
// 对称逻辑: b_row 沿 K 维变化 (用 threadIdx.y)

int b_row = t * TILE + threadIdx.y;
Bs[threadIdx.y][threadIdx.x] =
    (b_row < K && col < N) ? B[b_row * N + col] : 0.0f;

// 注意: B tile 不转置 — 保持 row-major 布局
// 后续计算用 Bs[k][threadIdx.x] (沿 K 遍历行)
第四章

Shared Memory Bank Conflict

Shared Memory 分为 32 个 bank，每个 bank 每 cycle 服务一个线程。同一 warp 的多个线程访问同一 bank 的不同地址 → bank conflict，串行化。

当前 Kernel (TILE=32) — 恰好无冲突

As[ty][k]: 同一 warp 所有线程有相同的 ty → 访问同一地址 → 广播，无冲突 ✓

Bs[k][tx]: tx = 0..31，行首对齐 Bank 0 → 32 个 bank 各一个 → 完美散开 ✓

何时出现冲突？

列方向访问 As[i][tx] → Bank# = (row×32) % 32 = 0 → 全部在 Bank 0 → 32-way conflict。

修复: __shared__ float As[TILE][TILE+1] — padding 一列打破 stride 对齐。

// ★ TILE=32 为什么没有 bank conflict？

// As[threadIdx.y][k] — same ty for entire warp
// → 32 threads read SAME address → broadcast → ✓

// Bs[k][threadIdx.x] — tx = 0,1,...,31
// Bank# = (k*TILE + tx)*4/4 % 32
//       = (k*32 + tx) % 32
//       = tx % 32  (k*32 is multiple of 32)
// → 32 unique banks → ✓ (这是巧合！因为 TILE=32)

// ● 列访问时的冲突:
// for (int i = 0; i < TILE; i++)
//     sum += As[i][threadIdx.x];  // column access!
// As[0][0], As[1][0], ..., As[31][0]
// Bank# = (row*32+0) % 32 = 0  → ALL in Bank 0 ☠

// ● Fix: padding
// __shared__ float As[TILE][TILE + 1];
// stride = 33 → Bank# = row%32 → spread out ✓
第四章 · 重要纠正

TILE_SIZE 由什么决定？— 三元博弈

约束硬件 (RTX 4060)TILE 上限
① Shared Memory 容量48 KB/Block
2×TILE²×4B ≤ 48KB		TILE ≤ 78
② 最大线程数1024 threads/Block
TILE² ≤ 1024		TILE ≤ 32
③ Register File65536 regs/SM
~32 regs×TILE² ≤ 65536		TILE ≤ 45

TILEMAX = min(78, 32, 45) = 32

"SRAM 决定 block_size" — 不完整

本周代码中 真正卡住 TILE 的是 1024 线程上限，不是 Shared Memory (TILE=32 只用 8KB/48KB)。

Block Size = Shared Memory、线程上限、Register 三者的最小交集。

如何突破 TILE=32？Thread-level Tiling

CUTLASS 用 256 线程 加载 128×128 Shared Memory tile:

  • 每个线程循环多次 + float4 搬运
  • 线程数约束 → 放松 ✓
  • Shared Memory 约束 → 收紧 (用更多)
  • Register 约束 → 收紧 (64 累加器/线程)

三个约束此消彼长 — 最优值由 Occupancy 决定。

多级 Tiling

Block → Warp → Thread — 每一层都让数据离算力更近一步
第五章

为什么需要多级 Tiling

第四章只做了一级 tiling (Global → Shared)。但 Shared Memory 本身也有 ~20 cycles 延迟。Shared Memory → Register 还能再加速 ~20 倍。工业级实现 (cuBLAS, CUTLASS) 使用三层 tiling：

Layer 1 — Block Tile (Global → Shared)
Tile: 128×128 或 32×32  |  延迟: ~400 → ~20 cyc  |  Block 内所有线程共享
Layer 2 — Warp Tile (Shared → Register)
Block tile 内切成 warp tile (64×64, 32×32)  |  延迟: ~20 → ~1 cyc  |  一个 warp 的 32 线程协作
Layer 3 — Thread Tile (Register 编排)
每个线程算 8×8=64 个 C 元素  |  64 个累加器在 Register  |  float4 向量化访存
为什么 Layer 2 很重要

Block tile 虽然存在 Shared Memory 比 HBM 快，但 ~20 cyc 的延迟累积起来仍然可观。内层循环跑 32 次 → 32×20 = 640 cycles。
如果把数据先搬进 Register，每次只要 ~1 cycle → 32×1 = 32 cycles — 又快了 20 倍。

第八章

当前 Kernel 的瓶颈在哪

Block-level tiling 解决了 Global Memory (~400 cyc) 的问题。但内层循环每次迭代仍然从 Shared Memory 读数据：

for (int k = 0; k < TILE; k++)
  acc += As[ty][k] * Bs[k][tx];
  // ↑ Shared Memory, ~20 cyc/次

TILE 次迭代累积的 Shared Memory 延迟 = 32 × 20 = 640 cycles。

如果数据在 Register (~1 cyc)：32 × 1 = 32 cycles — 再快 20 倍。

// 当前: 内层循环数据来自 Shared Memory
for (int k = 0; k < TILE; k++)
    acc += As[threadIdx.y][k]    // Shared → ~20 cyc
         * Bs[k][threadIdx.x];   // Shared → ~20 cyc

// Warp tiling 要做的事:
// 在内层循环之前，先把数据从 Shared Memory 搬到 Register

// Step 1: 从 Shared Memory 加载 fragment 到 Register
float a_reg[8];  // 8 个 A 元素在寄存器里
float b_reg[8];  // 8 个 B 元素在寄存器里
for (int i = 0; i < 8; i++) {
    a_reg[i] = As[ty*8 + i][k];  // 搬一次 (~20 cyc)
    b_reg[i] = Bs[k][tx*8 + i];  // 搬一次 (~20 cyc)
}

// Step 2: 在 Register 上做所有乘加
// 8×8 = 64 FMAs, 全部 ~1 cycle/次
for (int i = 0; i < 8; i++)
    for (int j = 0; j < 8; j++)
        c_frag[i][j] += a_reg[i] * b_reg[j];
// Reuse ratio: 64 FMAs / 16 shared loads = 4x

关键突破

64 线程 (8×8) → 线程约束被打破。Block Tile 反而从 32→64。Shared Memory / Register 成为新瓶颈。约束此消彼长。

#define BLOCK_TILE 64    // Block tile in Shared Memory
#define THREAD_TILE 8    // Each thread computes 8×8 C elements

__global__ void sgemm_warp_tiled(...) {
    __shared__ float As[BLOCK_TILE][BLOCK_TILE]; // 64×64×4B = 16KB
    __shared__ float Bs[BLOCK_TILE][BLOCK_TILE]; // 16KB, total 32KB

    int tx = threadIdx.x, ty = threadIdx.y; // 0..7
    int c_row = blockIdx.y * BLOCK_TILE + ty * THREAD_TILE;
    int c_col = blockIdx.x * BLOCK_TILE + tx * THREAD_TILE;

    float c_frag[THREAD_TILE][THREAD_TILE] = {0.0f}; // 64 regs
    float a_reg[THREAD_TILE], b_reg[THREAD_TILE];     // 16 regs

    for (int bk = 0; bk < K; bk += BLOCK_TILE) {
        // (1) Cooperative load: Global → Shared
        // 64 threads × loop iterations = fill 64×64
        int total = blockDim.x * blockDim.y; // 64
        for (int off = 0; off < BLOCK_TILE*BLOCK_TILE; off += total) {
            int idx = off + ty * blockDim.x + tx;
            int r = idx / BLOCK_TILE, c = idx % BLOCK_TILE;
            As[r][c] = (/*bounds*/) ? A[...] : 0.0f;
            Bs[r][c] = (/*bounds*/) ? B[...] : 0.0f;
        }
        __syncthreads();

        // (2) Inner loop: Shared → Register → Compute
        for (int k = 0; k < BLOCK_TILE; k++) {
            for (int i = 0; i < THREAD_TILE; i++)
                a_reg[i] = As[ty*THREAD_TILE + i][k];
            for (int j = 0; j < THREAD_TILE; j++)
                b_reg[j] = Bs[k][tx*THREAD_TILE + j];

            // Register × Register, ~1 cycle per FMA
            for (int i = 0; i < THREAD_TILE; i++)
                for (int j = 0; j < THREAD_TILE; j++)
                    c_frag[i][j] += a_reg[i] * b_reg[j];
        }
        __syncthreads();
    }
    // (3) Write back: Register → Global
    for (int i = 0; i < THREAD_TILE; i++)
        for (int j = 0; j < THREAD_TILE; j++)
            if (c_row+i < M && c_col+j < N)
                C[(c_row+i)*N + (c_col+j)] = c_frag[i][j];
}

Register Spilling 的后果

编译器把溢出寄存器的数据存到 Local Memory (物理上在 VRAM/HBM)。
你精心搬到寄存器里的数据，被退化成 "从 HBM 读" → 性能反而暴跌。

每个线程负责的 THREAD_TILE 越大 → Register 中 C fragment 越大 → 复用越多。但：

// THREAD_TILE = 8 → 64 C elements
// 64 (C_frag) + 8 (A_frag) + 8 (B_frag) ≈ 80 regs/thread ✓

// THREAD_TILE = 16 → 256 C elements
// 256 + 16 + 16 ≈ 288 regs/thread ✗
// RTX 4060: 65536 regs/SM
// 288 regs × 64 threads = 18432 → OK per SM
// But: 288 regs × 1024 threads (max block) = 294912 → exceeds!
// Compiler spills → performance tanks
nvcc -O3 --ptxas-options=-v -o gemm.exe gemm.cu

→ "Used 80 registers, 0 bytes spill stores" ✓

→ "Used 96 registers, 128 bytes spill stores" ✗ — 降低 THREAD_TILE
